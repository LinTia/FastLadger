# FastLedger 家庭智能记账系统 · 产品需求文档（PRD）

> 文档定位：需求基线，供产品评审、研发排期、测试验收对齐使用。
> 数据口径：所有金额在系统内**一律以整数「分」存储**（BIGINT），展示时再除以 100。
> 配套文档：`架构设计.md`、`数据库设计.md`、`API规范.md`、`开发计划.md`、`部署运维手册.md`（规划中）。

---

## 1. 背景（Background）

### 1.1 现状与痛点
- **数据不在自己手里**：主流记账 App 将数据存放在厂商云端，用户担心隐私、且厂商停服即数据丢失。
- **家庭多人记账难共享**：家庭开支由多人产生，但多数工具是"个人账本"，家人之间对账靠转发截图、手动合并。
- **记账门槛高、易放弃**：逐笔录入口繁琐，"今天花了多少"往往要回忆补记，准确率与持续性差。
- **投资与日常混在一起**：股票、基金、房产等资产散落在不同 App，家庭净资产缺少统一视图。

### 1.2 为什么自己搭
已有开源方案（如 ezBookkeeping、BeeCount）可自托管，但 FastLedger 强调**「截图即记账」的低门槛闭环 + 全家实时共享 + 隐私优先（数据不出本机，仅在识别失败时把账单文字发往用户自选模型）**，定位更贴近"非专业家人也能每天用"的家庭场景。

---

## 2. 目标（Goals）

### 2.1 产品目标
1. **隐私优先**：账本数据默认完全存储在用户自有设备（NAS/家用服务器），不依赖第三方云。
2. **3 秒记账**：付款后截图 → 自动识别 → 一次确认即可入账，把单笔成本压到秒级。
3. **全家实时共享**：一个账本多人协作，任一端记账，其他在线成员 1~2 秒内收到推送。
4. **资产全景**：日常流水 + 投资持仓（A股/港股/基金/黄金/房产）统一核算家庭净资产。

### 2.2 成功指标（KPI）
| 指标 | 口径 | 目标值（MVP 验收阈值） |
|---|---|---|
| 单笔录入耗时 | 从打开记账到确认保存 | ≤ 5 秒（理想 3 秒） |
| 识别准确率 | 金额/商户识别正确占比（抽样） | ≥ 90% |
| 识别失败率 | 需手动补全的比例 | ≤ 15% |
| 同步延迟 P95 | 一端保存 → 另一端收到推送 | ≤ 2 秒 |
| 周活跃记账天数 | 核心家庭用户每周主动记账天数 | ≥ 5 天 |

## 3. 目标用户与用户故事（User Stories）

### 3.1 用户画像
- **装维者（ tech-savvy 家庭成员）**：负责在 NAS 上部署、配置域名/HTTPS、管理账本与成员。
- **日常记账者（家人）**：日常消费主力，使用手机截图记账，不关心技术细节。
- **资产查看者（如配偶/长辈）**：主要查看家庭资产总览与报表，少量录入。

### 3.2 用户故事
1. 作为**日常记账者**，我希望拍下/截取付款截图后系统自动识别金额与商户，以便我 3 秒内完成一笔记账。
2. 作为**账本创建者**，我希望通过邀请码把家人拉进同一个账本，以便全家开支自动汇总。
3. 作为**日常记账者**，我希望在家人记账时我的页面实时刷新，以便随时掌握家庭花销。
4. 作为**投资者**，我希望记录股票/基金/房产并看到按当前行情折算的资产合计，以便掌握家庭净资产。
5. 作为**资产查看者**，我希望按分类/账户查看本月支出与预算执行，以便控制开销。
6. 作为**装维者**，我希望一键导出 CSV/JSON 备份，以便数据可迁移、不锁死。

## 4. 功能清单（Feature List）

### 4.1 账本与成员（MVP 核心）
- 创建账本、邀请成员（邀请码/链接）、成员角色（管理员/普通成员）、退出/移除成员。
- 一个用户可加入多个账本，切换账本查看。

### 4.2 账户与分类（MVP 核心）
- 资金账户：储蓄卡、信用卡、微信零钱、支付宝、现金（区分"资金账户"与"支付渠道"，避免重复记账）。
- 分类管理：支出分类（餐饮/交通/居家…）、收入分类；支持自定义。

### 4.3 交易（MVP 核心）
- 收入、支出、转账三类；转账在两端账户间原子调整余额。
- 每笔交易含：金额（分）、分类、账户、时间、备注、关联成员。
- 幂等：客户端 `client_uuid` 去重，断网重发不重复入账。

### 4.4 截图识别（MVP 核心，最高价值）
- 端侧 OCR 提取文字 → 端侧规则解析金额/商户/时间 → 展示**确认框**供用户校正后入账。
- 兜底：端侧无法识别时，把**账单文字（非图片）**发往用户配置的模型（OpenAI 兼容/本地 Ollama）解析。
- 隐私声明：明确"仅文字出网、图片不出本机"，并在首次使用时告知。

### 4.5 实时同步（MVP 核心）
- WebSocket 长连接：一端保存交易后，服务端 1~2 秒内推送给同账本在线成员并刷新其页面。
- 离线队列：无网络时本地暂存，恢复后按版本号增量补传/补拉。

### 4.6 投资模块（v0.2+）
- 标的（股票/基金/黄金/房产）、持仓、手动/自动行情更新、资产合计（含实物资产估值）。

### 4.7 预算与报表（v0.2+）
- 分类/周期预算、超支提醒；按月/分类汇总报表、CSV/JSON 导出。

### 4.8 账户与安全（贯穿）
- 注册/登录（JWT，可配置是否开放注册）；长期 API Token（供 iOS 快捷指令等）；可吊销。

## 5. 核心流程说明（Flows）

### 5.1 核心记账闭环（最高优先级）
```
用户截图付款 → 端侧OCR → 端侧规则解析(金额/商户/时间)
   ├─ 解析成功 → 弹出确认框(可编辑) → 用户确认 → 保存 → 服务端落库 → WebSocket 推送家人
   └─ 解析失败 → (可选)发送文字给LLM兜底 → 仍失败 → 用户手动录入
```

### 5.2 邀请成员
```
创建者生成邀请码 → 家人输入邀请码/打开链接 → 加入账本 → 双方可见共享账目
```

### 5.3 转账
```
选择"转账" → 选转出/转入账户与金额 → 服务端事务内原子调整两账户余额 → 生成一对关联交易
```

### 5.4 实时同步（断线恢复）
```
客户端保存时携带 client_uuid 与本地版本号
→ 服务端幂等写入并递增账本全局版本号
→ 在线成员经 WS 收到增量；离线成员重连后按 afterVersion 增量拉取
```

## 6. 交互说明（Interaction）

- **确认框是核心交互**：识别结果以"可编辑卡片"呈现，默认填充识别值，用户只改错的字段即可，降低确认成本。
- **实时刷新无感**：家人记账时，当前页以非阻塞方式插入新流水并动画提示"XX 刚记了一笔"，不打断操作。
- **离线优先**：无网时记账照常，本地队列显示"待同步 N 笔"，恢复后自动清空。
- **平台差异（重要）**：
  - Android：支持悬浮窗/全局截图，体验最佳。
  - Windows：客户端直接截图。
  - **iOS：受沙盒限制无全局截图**，截图记账走"照片共享扩展(Share Extension)"或手动选图，定位为"浏览/管理/手动记"客户端，不作为 3 秒闭环的主力端。

## 7. 数据指标与埋点（Metrics & Tracking）

| 埋点 | 触发时机 | 用途 |
|---|---|---|
| record_start / record_confirm | 打开记账 / 确认保存 | 计算单笔录入耗时 |
| ocr_success / ocr_fail / llm_fallback | 识别各阶段 | 识别准确率、失败率 |
| sync_push_latency | 推送送达 | 同步延迟 P95 |
| offline_queue_size | 离线队列长度 | 离线可用性 |

> 埋点数据默认仅存本地/自托管，不外发，符合隐私优先原则。

## 8. 验收标准（Acceptance Criteria，EARS 表述）

### 8.1 普遍约束（Ubiquitous）
- 系统应始终以整数「分」(BIGINT) 存储所有金额，不在任何层使用浮点表示钱。
- 系统应始终将账本数据存储于用户自有数据库，不在未授权情况下上传至第三方。

### 8.2 事件驱动（Event-driven）
- 当任一成员成功保存一笔交易时，系统应在 2 秒内将该交易推送给同账本的所有在线成员。
- 当用户提交截图时，系统应在 5 秒内返回识别结果或明确的失败原因。

### 8.3 异常/故障处理（Unwanted）
- 若端侧 OCR/规则无法解析金额，则系统应回退到用户配置的 LLM 文本兜底解析。
- 若 LLM 兜底仍失败，则系统应展示手动录入表单，且不丢失已识别出的任何字段。
- 若 WebSocket 连接断开，则系统应将新交易暂存本地队列，并在重连后自动增量补传与补拉。
- 若同一 `client_uuid` 重复提交，则系统应拒绝重复入账并返回首次结果。
- 若转账过程中任一账户更新失败，则系统应整体回滚，保证两账户余额一致。

### 8.4 状态驱动（State-driven）
- 当成员处于"已邀请未接受"状态时，系统应仅向其展示"接受邀请"入口，不展示账本内容。
- 当账户余额不足（如信用卡/储蓄扣减后为负，按业务规则）时，系统应正常记录并可在报表中标识。

### 8.5 可选功能（Optional）
- 若启用投资模块，则系统应计算并展示包含持仓与实物资产的家庭净资产合计。
- 若启用预算，则系统应在分类支出接近/超出预算时给出提醒。
- 若启用长期 API Token，则系统应支持基于 Token 的只读/写入访问，并支持单独吊销。

## 9. 范围与边界（Scope & Boundary）

### 9.1 MVP（v0.1）范围
- 必含：账本+成员、账户+分类、交易（收/支/转）、截图识别（端侧+LLM 兜底）、实时同步、Web/Windows 端。
- 暂不含（移至 v0.2+）：投资模块、预算、导出、iOS 全局截图闭环、2FA。

### 9.2 明确不做
- 不接入任何第三方云存储作为主存；不做多租户 SaaS。
- 不在未告知用户的情况下上传付款截图图片（仅文字可出网）。

## 10. 待确认问题（Open Questions）
1. 邀请成员跨公网的安全机制（邀请码有效期、最大成员数）？
2. 投资行情数据源与刷新频率、是否默认走外网？
3. 是否需要"账本锁定/只读归档"等家庭财务治理功能？
4. 多账本（如"家庭账"与"个人账"）的合并报表需求？
5. MVP 是否必须包含移动端 OCR，还是先以 Windows/Web 跑通闭环验证价值？

> 说明：以上问题涉及排期、资源与上线范围，需与相关负责人/家人确认后回填本 PRD。
