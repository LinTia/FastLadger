## 1. 项目是什么（一句话）

**FastLedger** = 一款**自托管**（部署在家庭 NAS / Docker）的**家庭智能记账与资产管理系统**。

- **核心闭环**：付款截图 → 端侧 OCR + 规则解析 → 人工确认预填 → 入账 → 家庭实时共享。
- **差异化卖点**：数据完全在自己手里、隐私优先（图片不上传，识别默认端侧完成）。
- **技术栈（规划）**：后端 Go + Gin + xorm + SQLite（预留 PG/MySQL）；客户端 Flutter（Win/Android/iOS）；Web 由后端 `go:embed` 托管；部署 Docker + Caddy 反代 + 自动 HTTPS。
- 详细定义见仓库根 [`README.md`](../../README.md) 与 `docs/` 下各文档。

## 4. 本项目的审阅约定（请务必遵守）

这是项目方与前面 AI 约定好的协作规范，照做能大幅减少无效往返：

1. **每条问题必须带 3 要素**：`文件路径` + `章节号/行号` + `原文片段或截图`。
   - ✅ 好："落地方案 §6.1 Lxxx：`ChangeBalance` 未显式用事务包裹，请确认并发安全。"
   - ❌ 差："转账可能不安全。"
2. **区分"断言"与"待确认"**：能 grep 源码/原型确认的，写肯定句并附证据；拿不准的，显式标 `[待确认]`，**不要写成"缺 / 找不到"的肯定句**（前一轮就因搜中文字面没命中就下"缺页"结论，造成误判）。
3. **用 CHANGELOG 追踪每条状态**：每条意见只有三种结局——`已采纳(附改动位置)` / `未采纳(附理由)` / `待确认`，不留悬空。
4. **跨文档一致性优先**：新版本最该防的是"A 文档改了、B 文档没跟上"，提问题优先查 PRD / 落地方案 / 新手指南 / 原型 四处口径是否一致。
5. **误判即时收回**：被证伪的意见在 CHANGELOG 标 `误判` 并简短说明，不硬撑。
6. **总体原则**（项目方原话）：**属实的修，误判的说理由，不盲目改。**

## 5. 已经确定的设计决策（除非有新证据，勿轻易推翻）

这些在 v1.1 已经定稿并落到文档/代码级，推翻需给出更强的新理由：

- **MVP 即支持多账本**：默认"家庭公共账本"，可新建"个人私账"并切换（统一了早期 PRD 写"单账本"的矛盾）。
- **增量同步机制**：账本级 `book_versions` 全局版本号 + 实体 `sync_version`，**写事务内原子 +1 并回写**；`sync/pull` 按 `afterVersion` 拉取。覆盖增/改/删。
- **隐私定位**：图片不上传；云端大模型仅作**可选兜底**且只传文本；原型零外部请求、可完全离线（已删除早期残留的字节系遥测脚本）。
- **并发冲突**：服务端权威 + 版本号，冲突返回 409，用户"覆盖 / 放弃 / 另存副本"三选一（家庭场景概率极低，不做 CRDT）。
- **金额用整数分存储**；SQLite 连接开 `WAL` / `busy_timeout` / `foreign_keys`；`ChangeBalance` 为单条原子 `UPDATE`。
- **录入耗时两口径**：OCR 响应 **< 3 秒**（设计目标，不含人工）；完整一笔 **≤ 15 秒**（验收阈值）。
- **自托管场景取舍**：`email` 改为可选（常无 SMTP）；移除 `transactions.geo_lng/geo_lat`（不再采 GPS）；`users` 表仅留 `password_hash`（bcrypt 内含盐，删独立 `salt` 列）。

### 8.1 范围与权威口径

阶段 4 的验收口径以 **`docs/FastLedger-开发WBS.md`「阶段 4：删除 / 恢复 / 审计」** 六项任务为唯一权威（4.1 回收站 30 天 TTL、4.2 整笔删/恢复 + **写幂等回执**、4.3 `audit_logs` 写入点、4.4 `Delete/Restore` 与 `Create` 对称、4.5 旧离线数据回流返 409、4.6 删除事务内动作）。另须遵守该节末尾的**归属哨兵约束**：`creator_uid = 0` 视为"仅 owner/admin 可见或可改"，禁止当作放行条件。

### 8.2 本轮已做（供核验，勿当作已背书）

- 修【致命】`mutateVisibility` 余额反转符号倒置（删除须取 Create delta 之负、恢复取正）。
- 修【静默算错】历史转账 `direction=0` 会导致删除时余额不回滚却不报错；新增迁移 `0006` 确定性回填 + Go 侧失败关闭。
- 迁移 `0005`：幂等回执加 `op` 维度，唯一键扩为 `(book_id, uid, op, client_uuid)`（走 `DROP INDEX` + `CREATE UNIQUE INDEX`，**不重建表**，以满足"老库升级不得删除旧回执"）。
- `Delete`/`Restore` 必填 `clientUuid`，与 `Create` 对称复用幂等回执。
- `ListDeleted` 回收站视图 + `PurgeExpiredTransactions`（只清到期墓碑）；`create` 审计 + `PurgeAuditLogs`（保留 1 年）；已删实体返 409 `ENTITY_DELETED`。

### 8.3 请你重点挑错的地方（自认最可能有问题）

1. **幂等键占用与失败回滚的边界**：占位写在加载目标行之前，若后续 404/无权限则整体回滚。请确认是否存在"占位已提交但回执未回写"的窗口，以及重试语义是否正确。
2. **`op` 维度是否真的够用**：目前 `op ∈ {create, delete, restore}`。若同一 `clientUuid` 被**不同用户**（uid 不同）使用，唯一键含 `uid` 故不冲突——请确认这是否符合预期（同一设备换账号登录时客户端可能复用 uuid）。
3. **回收站到期硬清除与同步的相互作用**：墓碑 30 天后被硬删，离线超过 30 天的客户端将**永远学不到该删除**。这是 PRD §12.1 的既定取舍，但请评估是否需要额外保护（如按 `sync_version` 判断是否已同步过）。
4. **`PurgeExpiredTransactions` 只按 `deleted_at` 判定**，不检查该墓碑是否已被所有成员拉取过。
5. **`0006` 回填依赖"转出侧先插入、id 较小"这一代码写入顺序**——若未来 `createTransferInTx` 调整插入顺序，回填规则会失效。请评估是否应改为显式落库而非依赖顺序。
6. **备份恢复审计是 best-effort（有意的取舍，请评估是否合理）**：`fastledger instance bump` 必须能在**没有数据库**时执行（《落地方案》§8.3：停容器→替换 db→bump→启动），所以它的审计失败只告警、不阻断，靠 `instance.meta` 的 `restore_epoch`+`restored_at` 兜底。请评估：恢复流程本身缺少 `audit_logs` 留痕是否可接受，还是应当改成"启动后由服务补记"。
7. **两个 0 哨兵的建模**：`audit_logs.book_id=0` 表示实例级事件、`actor_uid=0` 表示系统/运维操作（两列都是 NOT NULL、无"空"语义）。若你认为应当改成可空列或独立字段，请给出理由。
8. **登录审计置于签发令牌之前**：审计写失败就不签发令牌（避免出现"已认证但无留痕"）。代价是审计库异常会直接导致登录不可用——请评估这个可用性取舍。
