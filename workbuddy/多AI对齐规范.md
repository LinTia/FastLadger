# FastLedger 多 AI 协作对齐规范（颗粒度标准）

> **用途**：本项目由多个 AI 参与交叉评审与修复（WB / B / GPT / 第三个审阅者…）。本文件定义一套**最小颗粒度、编号、严重度、证据与状态标准**，让所有 AI 的意见能互相衔接、不重复、不冲突，且 owner（你）能高效裁决。
> **维护者**：WorkBuddy（WB）。**阅读顺序起点**：`README.md` → `第三方审阅者导读.md` → `CHANGELOG.md` → `gpt/` → `workbuddy/`。

## 2. 每条意见的最小颗粒度（必填字段）

任何一条 finding 必须包含以下字段，缺一视为"颗粒度不足、owner 可退回"：

| 字段 | 含义 | 示例 |
|---|---|---|
| `id` | 唯一编号（前缀+序号） | `GPT-R03` |
| `title` | 一句话问题 | 信用卡负债符号反向导致净资产虚增 |
| `severity` | 严重度 P0–P3 | `P1` |
| `location` | **文件路径 + 章节号 + 行号** | `docs/新手开发完整指南.md §13.1 ~L990` |
| `quote` | **原文片段**（证明你看的是此版本） | `account.Balance -= tx.Amount` |
| `problem` | 问题与根因 | 负债账户支出也减余额，符号错 |
| `reproduce` | 复现/验证步骤（能 grep 就 grep） | 储蓄1000+信用0，刷卡100→净资产1100 |
| `actual` | 实际行为 | 净资产虚增到 1100 |
| `expected` | 预期行为 | 净资产应仍为 900 |
| `impact` | 对用户/隐私/数据的后果 | 记账失真，信任崩塌 |
| `suggestion` | 建议修复 | 引入 `signedBalanceDelta` 按负债符号取反 |
| `status` | 待确认/已采纳/未采纳(误判)/已修复 | `已采纳` |
| `evidence` | 复核者核实结论（由复核 AI 填） | `WB 核实：属实，见 §13.1 修复` |

> **自检**：写完一条，问自己——"别人拿到这条，能否不读全文就定位、复现、裁决？"不能就补字段。

## 3. 严重度刻度（统一标尺，杜绝"我觉得很重要"）

| 级别 | 定义 | 处置节奏 |
|---|---|---|
| **P0** | 核心闭环不成立 / 数据损坏或丢失 / 安全被直接绕过 | 阻塞发布，立即修 |
| **P1** | 安全、隐私、会计正确性缺陷；上线前必须修 | 本版本内修 |
| **P2** | 跨文档一致性、健壮性、可维护性 | 后续版本排期 |
| **P3** | 优化建议、体验增强 | 可选 |

> 历史记录校准：GPT 首轮 18 项实际为 **11 项 P1、7 项 P2**，以 `gpt/findings.json` 为证；此前“全部 P1”的表述不准确。本轮新增 GPT-R19–GPT-R23 按同一标尺分级。严重度与验证范围都必须写明，隔离骨架问题不等同于已发生的生产事故。

## 4. 证据标准（杜绝"凭印象"）

- **所有"代码有 bug"的断言，必须附原文片段 + 精确位置**。没有原文的意见，owner 无法核对，等同无效。
- **禁止**"可能/大概/看起来/感觉这里不安全"等无证据泛泛而谈。
- **拿不准 → 标 `[待确认]`**，不要下肯定句（WB 的"两级分类误判"就是反面教材：搜中文字面没命中就下了"功能找不到"的肯定句）。
- **能用可复现脚本/反例证明的优先**（参考 `gpt/` 下的 Python 反例 + `findings/verification.json`）。

## 5. 状态机与去重（防重复劳动 + 防误判硬撑）

每条 finding 必须走完状态机，不留悬空：

```
待确认 ──┬─► 已采纳（附改动文件+章节+版本号）
         ├─► 未采纳（附拒绝理由）
         └─► 误判（收回，附简短说明，勿硬撑）
                      │
                      ▼
                 已修复（B 落地后由 CHANGELOG 记录）
```

- **提新意见前先搜重**：`grep` CHANGELOG + workbuddy + gpt，避免重复提已处理项（GPT 做到了——没重提 WB 已处理的"缺页/遥测"）。
- **已定决策勿推翻**：见 `第三方审阅者导读.md` 的"已定决策"清单（多账本口径、隐私定位、并发策略等），除非有新证据，否则不重开辩论。
- **误判即时收回**：被证伪时在 CHANGELOG 标 `误判` 并说明，保持诚实。

## 6. 文档口径优先级（一致性仲裁规则）

当四份文档说法冲突，按以下优先级裁决（**低优先级文档去对齐高优先级文档**）：

```
① 枚举字典.md      （字段/符号契约，高于一切字段语义）
② 落地方案.md      （权威技术设计）
③ PRD.md           （需求基线）
④ 新手开发完整指南.md（代码骨架，须随设计同步）
⑤ 原型             （演示用途，不约束实现）
```

> 转账技术专节：[入口裁决 GPT-ADR01](../docs/FastLedger-转账入口裁决.md)，由《落地方案》§6.1 引用，当前指南须按其单一入口和事务边界实现。

> **血泪教训（v1.1→v1.2）**：v1.1 只在 ①/② 修了同步版本号与事务，但 ④（新手指南骨架）仍是旧代码——照 ④ 写出的第一版代码仍带 R02/R06 缺陷。所以"设计对、骨架旧"= 没修。**任何设计改动，必须同步回骨架并记入 CHANGELOG。**

## 7. 共享术语与口径（统一语言，避免理解偏差）

| 术语 | 统一定义 |
|---|---|
| 金额单位 | **整数分**；`amount` 永远以分为单位，展示时 ÷100 |
| 负债符号 | 账户余额 **正 = 欠款**（欠 100 元时 `balance=+10000` 分），净资产 = Σ资产 − Σ负债 |
| 多账本 | 默认**家庭公共账** + 可建**个人私账**切换（v1.1 定，勿再改回"单账本") |
| 同步机制 | 基于 `book_versions` 全局版本号，客户端 `pull?afterVersion=` 拉增量 |
| 隐私定位 | 数据不出本机；云端**仅账单文字**经 LLM 兜底；原型必须可离线（已删遥测） |
| 可见性 | 成员可关闭"互看明细"，关闭时 WS 只发脱敏通知 |
| 幂等 | 创建命令经唯一 Create，以账本+用户+client_uuid 为键，核对完整内容并返回原结果 |
| 转账创建入口 | `TxService.Create`；HTTP 与离线 push 单项共用；内部 helper 不另开事务/加版本 |
| 版本实现 | 仅 `VersionRepo.Next`；Create、持仓与同步通过 `VersionSource` 使用 |

## 10. 新 AI 快速上手检查清单

1. 读 `README.md` 导航表 + `第三方审阅者导读.md`（背景、已定决策、协作约定）。
2. 读根 `CHANGELOG.md` —— **重点看 [1.6]–[1.12]（决策冻结）与 [1.13]–[1.24]（真实代码落地）**。
3. 读 `gpt/` 的 18 项 + `gpt/v1.4/`（R01–R18 与 GPT-R19–R23 均已被 WB 核实且已在代码中闭环，**勿重复提**）。

5. 读 `workbuddy/v1.2`–`v1.5-修复说明`（文档骨架阶段的改动与"能否开发"就绪边界）。
6. 读 `docs/FastLedger-开发WBS.md`（8 阶段任务分解 + §10 验收映射）。
7. **读真实代码 `server/`**（阶段 0/1/2 已落地）。优先看 `internal/service/tx.go`（唯一 Create / 转账双边 / 幂等）、`internal/database/database.go`（DSN PRAGMA + 启动校验）、`internal/api/`（400/409 映射与路由）、`internal/migrate/`（迁移机制）。

9. **先搜重、再提新**；不确定标 `[待确认]`。
10. 走完 **§5 状态机**；误判即时收回。
