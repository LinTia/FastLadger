## 一、跨文档一致性（最高价值，最该先对齐）

> 同一产品，PRD 与落地方案对"做什么"给出不同答案，会让研发/AI 不知道以谁为准。

### 1.1 【高】MVP 是否含"多账本"——两文档直接矛盾
- **证据**：PRD §3.2 MVP 写明「**单账本** + 成员（2 人）」；落地方案 §1.4 MVP 列「账本管理：创建/切换账本」、§8.6 v0.1 写「家庭公共账 + 个人私账」「支持多个独立账本」。
- **为什么重要**：这直接决定数据模型（是否要 `books` 多实例、切换逻辑、可见性粒度）和首版工作量，是范围基线，不能含糊。
- **建议**：二选一并对齐——若多账本是核心卖点（定位里强调），**把"多账本"写进 PRD 的 MVP**；若想砍首版范围，则**把多账本移到 v0.2** 并从落地方案 MVP 移除。同时更新 §3.3 路线图与 §1.2 用户故事。

### 1.2 【中】"录入耗时"目标冲突：3 秒 vs 15 秒
- **证据**：落地方案 §1.1「3 秒内完成一笔」「截图秒记」；README 产品特性「截图秒记」；PRD §2.3 却写「录入耗时 ≤ 15 秒（【假设】）」。
- **建议**：PRD 作为口径基线，应明确区分**设计目标（3 秒理想）**与**验收阈值（如 ≤ 15 秒）**，不要把两个数字散落在不同文档互相打架。

### 1.3 【中】并发冲突策略：PRD 标"待确认"，落地方案已拍板
- **证据**：PRD §9 #5「多端并发编辑同一笔……（【待确认】策略）」；落地方案 §3.5 已定「以最后修改 + 版本号为准，同版本冲突后提交覆盖并提示」。
- **建议**：落地方案已决策，PRD §9 与 §12 待确认问题第 3 条应**同步划掉/更新**，保持评审稿与执行方案一致。

### 1.4 【低】可见性粒度：PRD 仅账本级，落地方案多一个成员级覆盖
- **证据**：PRD §7.3「账本默认互看；提供开关」；落地方案 `books.members_can_view_others`（账本开关）+ `book_members.can_view_others`（成员级覆盖，**预留**）。
- **建议**：PRD 补一句"成员级可见性为预留字段"，避免读者以为 MVP 就要做成员级精细控制。

### 1.5 【低】原型页面数口径：说"12 页"却列了 13 项
- **证据**：`prototype/README.md` 与 `README.md` 均称「12 个核心页面」，但清单列了 登录/首页/截图识别/手动记账转账/交易详情/账户/两级分类/投资资产/预算/报表/导出/家庭成员/我的设置 = **13 项**（截图识别通常并入首页记账流）。
- **建议**：统一口径，或说明"截图识别是首页的子流程，不单列"。

## 二、数据模型 / 技术设计优化

### 2.1 【高】同步全局版本号递增机制仍未定义（上一轮遗留）
- **证据**：`transactions.version INTEGER DEFAULT 1`（落地方案 §4.5）；`sync/pull?afterVersion`（§5.1）；但**全文没有任何地方说明 `version` 在每次写入时如何递增**，也没有 `book_versions` 之类的账本全局版本表。
- **为什么重要**：`pull` 依赖"全局有序版本"做增量拉取。若每笔交易 `version` 恒为 1，离线补传/断线补漏拿不到正确增量，实时同步承诺不成立。
- **建议**：引入账本级全局单调递增版本（如 `book_versions(version BIGINT)` 或 `books.version`），每次写操作原子 +1 并写入交易；`pull` 按全局版本过滤。这是上一轮就指出的 P0，本版仍未闭合，请重点处理。

### 2.2 【中】`users` 表 `password_hash` + 独立 `salt` 列——与 bcrypt 语义冲突
- **证据**：落地方案 §4.5 `users` 表同时有 `password_hash VARCHAR(128)` 与 `salt VARCHAR(16)`。
- **为什么**：bcrypt/argon2 的输出**已内含 salt**，再加独立 salt 列要么冗余（列空着），要么暗示自研"哈希+salt"（弱于现成算法）。新手容易踩坑。
- **建议**：直接用 bcrypt/argon2（输出单字段存 `password_hash`），**删除 salt 列**；或在文档明确"采用 X 算法，salt 列废弃/仅供未来算法"。

### 2.3 【中】`email` 必填 + 唯一 + `email_verified`——自托管家庭场景过度
- **证据**：`users.email NOT NULL UNIQUE` + `email_verified`（§4.5）；但产品是 2~5 人的家庭 NAS 实例，注册常关闭（§8.1 `EBK_ENABLE_REGISTER=false`），成员靠邀请码加入。
- **为什么**：强制邮箱+唯一+验证，对"家里人加个账本"是摩擦；邮箱验证流程（发信）在自托管环境往往没配 SMTP，会变成死功能。
- **建议**：邮箱改**可选**；删除或默认关闭 `email_verified` 相关流程；若需找回密码再引入。

### 2.4 【中】`transactions.geo_lng / geo_lat` 默认每笔记定位——与隐私定位矛盾
- **证据**：`transactions` 表含 `geo_lng REAL, geo_lat REAL`（§4.5）。
- **为什么**：隐私是核心卖点（"数据不出本机"），但给每笔交易默认打 GPS 点是隐私过度采集，且 MVP 无明确用途（报表/对账不需要定位）。
- **建议**：MVP 移除该字段，或标记为**默认关闭的可选能力**并在隐私章节说明采集范围。

### 2.5 【低】`accounts.parent_id`（两级账户）语义不清
- **证据**：`accounts` 表有 `parent_id DEFAULT 0` 注释"两级账户"（§4.5），但全文叙事聚焦的是 `category`（15 类账户分类），并未解释账户为何需要层级（如：投资账户下挂子账户？）。
- **建议**：明确 `parent_id` 的用途（或仅用于投资账户分组），否则 MVP 应去掉，避免"为扩展而扩展"。

### 2.6 【低】持仓数量/价格用 `VARCHAR(48)` 存储
- **证据**：`holdings.quantity / current_price` 为字符串（§4.5），`market_value BIGINT`（分）。
- **建议**：保留字符串以避精度损失可以，但必须在文档/代码约定**所有价格运算走 decimal 库（如 shopspring/decimal），严禁 float**；或改用整数缩放存储（如价格×精度）。这是记账系统的精度命门，值得一句强约束。

### 2.7 【低】`ChangeBalance` 须确认为原子 UPDATE
- **证据**：§6.1 `account.ChangeBalance(sess, ...)` 被调用，但未展示实现。
- **建议**：明确实现为「`UPDATE accounts SET balance = balance ± ? WHERE id = ?`」（数据库内原子），而非"先读后写"，以防家庭并发记账丢更新。

### 2.8 【低】SQLite 初始化未显式开启 WAL / 备份一致性
- **证据**：§4.5 建表 SQL 与 §8.3 备份（`VACUUM INTO` / `.backup`）均未提 `PRAGMA journal_mode=WAL` 与 `busy_timeout`。
- **建议**：在初始化章节补 `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;`，提升家庭多端并发写入安全性。

### 2.9 【低】首个管理员/账本如何引导创建未写清
- **证据**：§8.1「初始账号建好后关闭公开注册」暗示存在初始账号创建路径，但 PRD §4.1「首次注册引导」与落地方案均未说明**默认关闭注册时，第一个 owner 怎么来**（CLI `userdata`？首启开放？）。
- **建议**：补一小节"初始化引导"：首启开放注册建 owner→自动建默认账本→关闭公开注册；或提供 `./fastledger user create --admin` 命令。

## 三、原型本身（重点："以原型为准"那块）

> 原型是某原型工具（字节系，含 slardar/tea 遥测）导出的**构建产物**，非手写源码。

### 3.1 【高】原型内嵌第三方遥测，与"隐私优先"定位矛盾，且破坏离线
- **证据**：`prototype/index.html` 注入 `slardar`（lf3-short.ibytedapm.com，字节 APM）与 `collectEvent/tea`（bytescm.com，字节分析）；`prototype/README.md` 却称"纯前端、可离线、数据存 localStorage"。
- **为什么重要**：
  1. **立场冲突**：一个主打"数据不出本机"的产品，其原型本身在向外（字节）发遥测；
  2. **离线不成立**：这些外部脚本在 `file://` 或离线时会请求失败（README 自己也说"控制台报错属正常"），所谓"离线查看"打了折扣；
  3. **分享风险**：若把原型发给他人评审，使用行为会回传字节。
- **建议**：从原型构建里**移除/禁用遥测脚本**；若需演示数据，改用本地 mock。并在仓库注明原型来源工具与"已去遥测"。

### 3.2 【中】原型是导出产物，仓库无可编辑源
- **证据**：`prototype/` 只有 `index.html` + 哈希化 JS/CSS 包，无可读源码；README 称"由在线原型导出为本地静态资源"。
- **为什么**：原型若需迭代（按本评审改交互），在仓库里**无法直接改**——得回原工具改再导出，容易版本漂移。
- **建议**：要么把原型**源工程**一并入库（或链接），要么在 README 注明"源在 XX 工具，本目录为导出快照，请勿手改"。

### 3.3 【低】"两级分类""我的设置"两页需核实是否真做了
- **证据**：对 `index-DNvhksAn.js`（1.5MB）检索，「截图识别/预算/成员/投资/报表/导出/转账/登录/首页」均命中，但字面「两级分类」「我的设置」**未命中**（可能用别的文案，如"分类""设置"）。
- **建议**：在原型里实际点一遍确认这两页存在且可用；若只是文案不同，更新 README 清单即可。

### 3.4 【低】原型"离线"声明与事实不符
- **证据**：见 3.1。
- **建议**：如实改为"需本地静态服务器运行；联网时会尝试加载第三方脚本，失败不影响交互"，避免误导。

## 四、结构 / 流程优化

### 4.1 【低】落地方案 与 新手指南 内容重叠、可能漂移
- **证据**：两者都讲栈、DB、API、代码骨架；落地方案已含"关键代码骨架"（§6.1/§6.2）。
- **建议**：明确分工——**落地方案=架构与决策（为什么）**，**新手指南=可照敲步骤（怎么做）**，并在两文互相注明"以落地方案为准，指南仅作实现示例"，避免将来改一处漏一处。

### 4.2 【低】缺统一的"枚举字典"
- **证据**：`tx_type / payment_channel / role / account.category(15类)` 分散在 PRD §6、落地方案 §4.2/§4.5/§5 多处。
- **建议**：单列一张**枚举字典表**作为唯一真相源，PRD 与落地方案都引用它（也方便原型/前端对照）。

### 4.3 【低】KPI 缺"怎么度量"
- **证据**：PRD §2.3 列了识别确认率、录入耗时、周活跃天数等，但**没有度量方法**（埋点？手工？），落地方案 §7 测试也未覆盖这些产品指标。
- **建议**：补一节"指标度量方案"：识别确认率=确认即保存/总识别次数；录入耗时=打开记账到保存的时间差（前端打点）；这些打点默认**仅在自托管实例内**，不外发。

### 4.4 【低】缺 CHANGELOG / 版本标记
- **证据**：仓库无版本标签或变更记录。
- **建议**：加 `CHANGELOG.md` 或在 README 标注文档版本，便于多 AI/多人协同时对齐"看的是哪一版"。

## 六、给"另一 AI 交叉评审"的协同提示

1. **先对齐一·1（MVP 多账本）**：这是范围基线的分歧，建议两位评审者先就"首版到底做不做多账本"达成一致，其余文档围绕结论修。
2. **同步版本号（二·1）是反复出现的技术债**：上一轮提过、本版仍未闭合，请作为联合重点验证"离线补漏/实时同步"是否真的能跑通。
3. **隐私一致性是产品立足点**：PRD/落地方案 都强调隐私，但**原型本身破了例（三·1）**，且 `geo_lng/geo_lat`（二·4）、LLM 外发文字都值得在"隐私威胁模型"一节统一讲清"什么出网、什么不出"。
4. **可交付分工建议**：A 负责"文档口径与决策一致性"（第一、四层），B 负责"技术模型与隐私正确性"（第二、三层），最后合到一份 CHANGELOG。
