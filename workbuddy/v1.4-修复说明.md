## 3. 关键修复详解

### 3.1 P2：`Transfer` 对称幂等（闭环 R04 在转账路径的缺口）

**修复前（v1.3）**：`func Transfer(uid, bookID, fromId, toId, amount int64) error`，内部**完全无幂等**——不捕获 `clientUuid`、不查 `idempotency_records`、不写回执。端侧离线补传或对账时若重试转账，会**重复扣款 + 重复加款 + 产生两对转账记录**。

**修复后**：
```go
func Transfer(uid, bookID, fromId, toId, amount int64, clientUuid string) error {
    // 0) 幂等（R04）：clientUuid 非空时，先查操作回执（ResultType=2 标记转账）
    if clientUuid != "" {
        rec := &models.IdempotencyRecord{}
        has, _ := sess.Where("book_id=? AND uid=? AND client_uuid=?", bookID, uid, clientUuid).Get(rec)
        if has {
            if rec.RequestHash != transferHash(fromId, toId, amount) {
                sess.Rollback(); return errors.New("同一 client_uuid 对应了不同请求内容")
            }
            return sess.Commit() // 重试，原业务已生效，返回成功（不产生第二笔）
        }
        rec = &models.IdempotencyRecord{ /* ResultType: 2, RequestHash: transferHash(...) */ }
        if _, err := sess.Insert(rec); err != nil {
            sess.Rollback(); return nil // 撞唯一约束 = 并发重试，返回其结果
        }
    }
    // ... 账户校验 → nextBookVersion → 原子改两侧余额 → 插两条交易 ...
    if clientUuid != "" {
        sess.Exec("UPDATE idempotency_records SET result_ids=? ...", fmt.Sprintf("%d,%d", out.Id, in.Id), ...)
    }
    return sess.Commit()
}

func transferHash(fromId, toId, amount int64) string {
    raw := fmt.Sprintf("%d|%d|%d", fromId, toId, amount)
    sum := sha256.Sum256([]byte(raw))
    return hex.EncodeToString(sum[:16])
}
```

**设计要点**：
- 与 `AddTransaction`（§13.1）共用 `idempotency_records` 表，但用 `ResultType=2` 区分转账；唯一键 `(book_id,uid,client_uuid)` 由 `ResultType` 外的字段构成，因此**同一 client_uuid 若先用于交易后用于转账会被正确判为冲突**（不同操作不应复用同一幂等 key）。
- 占位失败（撞唯一约束）= 并发的另一请求已占位 → 本次视为重试，返回 `nil`（其业务已在该并发请求中执行）。
- 业务失败回滚时占位一并回滚，重试可重新占位，逻辑自洽。

### 3.2 P3：§22.1 统一版本号入口

**修复前（v1.3）**：§22.1 手写了一份 `INSERT INTO book_versions ... ON CONFLICT(book_id) DO UPDATE` upsert，与 §13.1 `nextBookVersion` 是**同一段逻辑的两份实现**，日后必漂移。

**修复后**：§22.1 改为"统一调用 `nextBookVersion`（§13.1）"并加约束说明，正文内不再出现手写 upsert（全仓库仅 §13.1 L1087–1088 保留一份实现）。

### 3.3 P3：幂等契约强化

在 §13.1 `AddTransaction` 入参处新增注释：所有经 handler 进入的**写请求必须携带 `client_uuid`**；未携带退化为非幂等（仅允许服务端内部直接调用）；端侧离线补传/重试务必带 `client_uuid`。

### 3.4 P3：R18 描述合并

R18（WS 并发锁顺序/清理）实际由 **v1.2** 修复；v1.3 仅补充并发清理细节。本轮在 CHANGELOG `[1.4]` 明确"二者为同一修复、合并口径"，不篡改历史条目。

## 5. 未改 / 遗留（开放项）

1. **运行时验证空白（最大鸿沟）**：最小后端骨架可编译、`go test -race` 覆盖 WS 与并发、`Transfer` 幂等并发重试集成测试、真实 SQLite DSN 行为（ON CONFLICT / xorm `Exist` / `SumInt`）均待执行。**建议下一轮优先攻此**。
2. 枚举字典与新增字段（`ResultType`/`restore_epoch`）的最终核对。
3. `prototype/` 仍是字节系工具导出的构建产物，无可编辑源码——是否源码化可评估。
4. **⚠️ 待确认（转账入口跨文档分歧）**：本项目的转账入口在两份文档里是**两套模型**——`落地方案 §6.1`（L977）把转账作为统一 `Create` 事务内的分支，经 `s.createRelatedTransfer(sess, req, newVersion)` 生成对侧记录；而 `新手开发完整指南 §13.2` 是一个**独立的 `Transfer` API**（改两侧余额 + 插两条记录），且 §13.1 的 `AddTransaction` 并不在 `TxType==3` 时生成对侧。这是 v1.1→v1.3 历轮都**未统一**的架构分歧。
   - 本轮 P2 的幂等加在 `Transfer`（§13.2）上；但若最终转账主入口是落地方案的 `Create→createRelatedTransfer` 路径，则该路径**仍需补 `clientUuid` 幂等参数**（当前 `createRelatedTransfer(sess, req, newVersion)` 不带）。
   - **建议裁决**：明确转账的最终入口是哪个函数，并据此把幂等参数/回执逻辑统一到唯一路径上，避免"修了 Transfer 却没接入口"。该分歧超出本轮 P2/P3 修复范围，故标注待 GPT 及协作者裁决，未擅自改动架构。

## 6. 给 GPT（及后续 AI）的审核提示

请重点核对以下风险点（按 `多AI对齐规范.md` 字段格式提）：

1. **P2 幂等闭环**：§13.2 的 `Transfer` 幂等是否真正无遗漏？尤其——占位成功但随后业务失败回滚后重试是否会正确重做？并发撞唯一约束返回 `nil` 是否安全？
2. **`transferHash` 与 `requestHash` 分离**：分离是否必要且正确？若合并为单一 hash 函数是否更优（当前分离是为避免交易/转账误判冲突，是否有更好的统一方案）？
3. **§22.1 统一是否彻底**：是否还有第三处版本号递增实现被遗漏（除 §13.1 `nextBookVersion` 外）？
4. **契约约束力**：仅靠注释"写请求必须携带 client_uuid"是否足够？是否应在 handler 层做**强制校验**（缺 client_uuid 直接 400），而非依赖文档约定？
5. **函数签名变更的传播**：`Transfer` 新增 `clientUuid` 末参，handler/路由调用点是否需同步修改？建议核对 `docs/` 内所有 `Transfer(` 调用处。
