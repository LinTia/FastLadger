# GitHub 自带 CI 能验证什么、不能验证什么（R0 证据口径）

> 结论先行：**"构建 / 静态检查 / 全量单测 / 全仓竞态 / 容器冒烟"这类"进程退出码即结论"的事，全部可以、也应该交给 GitHub 自带 CI**——它跑在干净 Linux + CGO 环境，有 run URL，第三方点开就能复核。
> 但 **A（R0-E-35 独立复验）、C（228 条逐控件运行时）以及 B 的成对截图**属于"有人在真实浏览器里操作并观察"的验证，**Go 测试 CI 无法替代**；把它们标记为完成会构成伪证。

## 2. 为什么 A / C 不能"顺手 CI 化"

| 障碍 | 具体表现 |
|---|---|
| 需要"失败态"构造 | 要验证 503、网络拒绝、慢网、恢复中，必须能操纵后端行为（注入故障），CI 里没有这个开关 |
| 需要真实浏览器 + 登录态 | Web 是原生 JS SPA + `localStorage` 令牌；CI 里要起后端、种子化、注入令牌、按视口采集，属于新建一条流水线 |
| 需要多角色/多会话 | 至少 owner / admin / member 三种角色与并发会话，凭据与隔离要求高 |
| 结论是"观察"不是"退出码" | 逐控件验收要判断"点了之后是否符合原型"，不是 pass/fail 断言，必须有人或断言脚本判定 |

## 3. 因此的状态口径（不得混用）

- **包 D = PARTIAL**：CI 已原生证明"构建/静态检查/全量单测/全仓 race/容器冒烟"，这部分**不再是缺口**；仍缺的是**逐路由独立断言**（覆盖 3 / 部分 5 / 未覆盖 5）。
- **包 A = BLOCKED**、**包 C = BLOCKED**：与 CI 是否通过无关，CI 全绿也不改变这两个状态。
- **包 B = PARTIAL**：截图数量与采集成功 ≠ 同数据同角色同状态全覆盖。
- **R0 整体仍 BLOCK**，不授权 R1–R7。

## 4. 若后续要把 B 也接进 CI（可行性备忘，本轮未实施）

需要依次解决：① 启动后端 + `db migrate` + 种子数据（脚本已有：`tools/r0/seed-from-dataset.js`）；② headless 浏览器（runner 可用 Playwright/Chromium）；③ 注入登录态（实现侧 `localStorage.fl_token`、原型侧 toolkit 命名空间前缀需运行时探测）；④ 采集产物上传 `actions/upload-artifact` 并生成 manifest。工作量约等于一条独立流水线，且**仍不能替代 C**（验收判定仍需人或断言脚本）。
