## 2. 已独立确认的正确结论

### 2.1 四条 FAIL 的 runner 判定确实不是可靠的运行时验收

复核 `tools/r0/e2e/specs/c-controls.js`：

- `I-LOGIN-04` 在 `groupLogin` 中被无条件赋值为 `bad(...)`；前面取得的密码框 locator / type 值没有用于判断显隐控件。
- `I-LOGIN-11`、`I-LOGIN-12` 没有显式运行时断言，依赖 `classifyMissing()` 读取 fixture 的静态文字生成 FAIL。
- `I-HOME-01` 在 `groupHome` 中被无条件赋值为 `bad(...)`；虽读取了页面文本，但没有消费该值来判断账本切换控件。

因此报告关于“4 条 FAIL 均非可信运行时断言”的核心发现成立。当前日志 detail 中声称“本轮确认浏览器中不存在控件”等字样，不能当成真实 DOM 观测。

### 2.2 登录页密码显隐不是已确认需求

PRD 与 Web 设计规范登录交互条款没有要求登录 / 注册密码显隐按钮；现有前端登录页的密码框固定为 `type=password`。将“登录页显隐按钮缺失”直接视为已确认产品缺陷，证据不足。

所以，`I-LOGIN-04` 不应仅凭 R0-E-39 的二次复核登记或通用 UX 惯例认定为已确认产品缺陷。是否纳入产品需求，确实需要 Owner 决策。

### 2.3 邀请 API 事实大体准确

当前后端确有公开的 `POST /api/v1/books/:id/members/join`，在 JWT 鉴权组之外；请求体字段为 `code / username / email / password`。join 成功返回用户 DTO，不直接返回 access token。邀请失效、账本错配等对外错误采用统一响应，限流与审计规则也有服务端实现。

报告提醒不得臆造 `/invite/.../redeem` API、不得拆分防枚举错误、不得改变邀请规则，是正确的。

### 2.4 fixture 抽取脚本确有转义竖线解析风险

`tools/r0/e2e/scripts/extract-controls.js` 的 `cells()` 直接使用 `line.split('|')`，没有处理 Markdown 表格单元格中的转义竖线。报告展示的字段污染与后续 `classifyMissing()` 降级路径，技术因果链有代码依据。

不过本轮没有重新执行抽取脚本或重建 fixture；该因果链仍应标记为源码静态确认、待独立复跑，而非运行时复现。

## 3. 必须补正的实质问题

### P1-1：邀请功能的“已定需求”与“登录页入口形态”被混在一起

报告一方面正确引用 PRD §12.1 [1.12]：邀请链接直达注册、展示账本名与邀请人、设置用户名 / 密码、原子创建 user 与 book_members；另一方面又把 `I-LOGIN-11/12` 的主分类写成“需求待 Owner 裁决”，并列出 5 项邀请主题 Owner 待裁决事项。

这里必须明确拆成两个对象：

1. **登录页第三入口 / 在登录页输入邀请码**：PRD 没有要求这种控件形态。C 对“登录页内必须有邀请码输入框”的验收域不成立，应归为测试口径问题 / 需求外观察，而不是已确认缺陷。
2. **PRD §12.1 已明确决定的邀请链接入户流程**：报告 §6.1 自己确认 Web 当前没有链接落地、邀请详情展示及 join UI。这个流程不是待 Owner 决定是否需要的 UX 建议，而是**已确认需求尚未在 Web 端实现的独立功能缺口**。

建议将矩阵修正为：`I-LOGIN-11/12` 的“登录页控件检查”属于测试口径问题；另列“PRD §12.1 邀请链接注册流程未接入 Web”为确认缺口（不把它伪装成这两条 C FAIL 的运行时结果，也不擅自改动 C 状态）。

Owner 只需裁决**偏离 PRD 的方案**，例如是否允许省略账本名 / 邀请人展示、是否接受某种公开邀请预览 API 的安全设计；不应把“邀请链接入户功能是否存在”重新列为待裁决事项。PRD 已经作出决定。

### P1-2：D-3 顶栏账本切换已是 Owner 决策，不应再列为“是否需要”的待裁决

报告已确认：

- D-3 已决定账本切换放在顶栏；
- UI-DESIGN-01 §4.6.1 / §9.2 将“顶栏右侧账本切换”固定为设计执行；
- 当前 `index.html` 中 `#navBooks` 初始带 `hidden`，`showNav()` 只移除其他导航项的 hidden，从未移除 `#navBooks` 的 hidden；
- `style.css` 的 `.hidden` 是 `display:none!important`。

因此，**顶栏显式账本切换控件未实现 / 不可见**不是“是否需要由 Owner 决定”的问题，而是已裁决设计尚未落实的独立实现缺口。

`I-HOME-01` 本身要求“首页内容区内有切换控件”，与 D-3 的顶栏位置不一致；将这条 C 用例判为测试口径问题是合理的。但这不能抵消另一个事实：D-3 要求的顶栏切换控件当前不可见。

报告 §4.9 第 3 项把“D-3 顶栏账本切换是否应作为另一条独立缺口登记”交给 Owner，表述应改为：缺口本身已经由既有 Owner 决策和当前源码共同确定；Owner 如需裁决，只涉及具体 UI 实施方案或范围，不涉及是否需要顶栏切换。

另需修正 §4.7 / §4.8 的测试方案：`#brand → #books` 只是回到账本列表，不等同于顶栏账本切换控件。不能以品牌点击可进入账本列表，代替对 D-3 顶栏切换器的验收。移动端“我的 → 我的账本”可以是移动端入口，但不替代桌面端已定的顶栏入口。

### P1-3：对“无需求”的项目仍提出必须通过运行时断言证明存在，逻辑不一致

报告 §2.5 认定密码显隐控件没有 PRD / 设计规范条款，§2.8 又将“是否纳入需求”留给 Owner；但 §2.7、§5.5 同时要求测试必须断言显隐控件存在并能切换，否则维持 FAIL。

这两种口径不能同时成立：

- Owner 尚未决定纳入时，测试不能把一个未承诺的 UX 控件作为必过项；
- 若 Owner 决定纳入，再把它作为正式需求补入 PRD / 设计规范，并定义范围后，测试才应按该需求断言；

同样的逻辑适用于 `I-HOME-01` 的“首页内部另设切换控件”：若该位置与 D-3 冲突，测试应验证 D-3 的顶栏入口，而不是要求首页内部重复控件。

报告可以保留当前 4 条历史 FAIL 作为原始基线，但不能要求未来 runner 永久对不属于需求的控件做存在性断言。应把“历史状态保留”与“后续验收规则”分开写清楚。
