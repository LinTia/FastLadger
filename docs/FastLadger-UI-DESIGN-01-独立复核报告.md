## 2. 必须修正的问题

### UIREV-01｜P1：桌面导航建议与已裁决 D-3 正面冲突

**证据**
- 《FastLedger-R0-收尾执行清单.md》D-3 明确为：移动端 4 Tab：首页 / 记一笔 / 报表 / 我的；桌面端 5 项顶部导航；账本切换置于顶栏。
- 视觉规范 §4.1 却规定桌面左侧固定 232px 主导航。
- UI-DESIGN-01 §4 冲突 2 识别了冲突，但推荐方案 C（侧栏承载 5 项主导航），这仍然把“顶部导航”改成了“侧栏导航”，并非保留 D-3。

**影响**
若直接执行方案 C，会未经 Owner 授权改变已裁决的信息架构；“保留 5 项数量”不能替代“保留顶部导航位置”这一明确决策。

**修订要求**
1. 当前执行基线必须严格遵守 D-3：桌面保留 5 项顶部主导航，账本切换在顶栏。
2. 侧栏不得作为这 5 项主导航的替代实现。低频入口可另行设计为“更多”菜单/分组入口，但不得擅自扩成第 6 个主导航项。
3. 同步修订视觉规范 §4.1，使其与 §4.3、D-3 一致；报告 §4 冲突 2 不应再把侧栏方案 C 作为推荐实施方案。
4. 如确实希望改为侧栏，必须先由 Owner 明确修订 D-3，并同步权威决策文档；WorkBuddy 不得自行裁决。

### UIREV-02｜P1：02a“可先行”与 R0 门禁互相矛盾

**证据**
- 报告 §7 前置门禁写明：UI-DESIGN-02 及之后代码改造必须等 R0 放行或 Owner 明确授权。
- 同一节依赖图又写“02a 设计令牌（无 IA 依赖，裁决前即可准备）”。
- 02a 的实际范围不是纯文档准备，而是修改 `server/web/dist/style.css` 的 `:root` 与新增深色主题区块，并要求全站主色/底色发生变化。

**影响**
这会让执行者误以为只要没有 IA 冲突就可以先改 CSS。实际 CSS 变更会改变 R0 的页面外观与截图基线，造成审计基线漂移；即使不改 DOM/API，也不是纯设计准备。

**修订要求**
1. 将“02a 可先行”限定为**文档/令牌表/映射方案/脚本设计**，不得修改任何运行时代码。
2. `style.css`、`index.html`、`app.js` 的任何改动均须等 R0 放行，或取得 Owner 对具体文件/范围/验收方式的书面例外授权。
3. 若未来获准改 CSS，先冻结 R0 所需基线截图、SHA 和测试证据，并明确该次 UI 改造与 R0 验收证据的隔离策略；不能覆盖或替换既有证据。

### UIREV-03｜P1：D-3 移动端 4 Tab 与“中央新增主操作”需明确为同一套 4 槽设计

**证据**
- D-3 已裁决移动端 4 Tab，其中明确包含“记一笔”。
- 视觉规范 §4.2 又规定底部导航包含高频入口，并把“新增/记一笔”作为中央突出主操作。
- 报告 §4 冲突 1 的方案 A 是四项：首页 / 记一笔 / 报表 / 我的；方案 C 则可能形成 4 Tab 加额外 FAB 的五个可见入口。

**影响**
如果将“记一笔 Tab”与独立 FAB 同时呈现，可能形成五个槽位或重复入口，违反 D-3 的 4 Tab 约束。

**修订要求**
1. 明确底部导航的四个目的地就是 D-3 的四项；“记一笔”可以视觉上突出，但不得再额外增加第五个导航槽。
2. 如果 FAB 仅是“记一笔”Tab 的视觉呈现/触发器，需在规范中写明它不构成第五个 Tab，且不得重复出现两个独立的记账入口。
3. 交易总表必须位于“我的”下作为辅助检索入口，遵守 D-6，不得回到底栏主导航。

### UIREV-04｜P2：视图数量统计口径不准确

**证据**
报告 §3.1–§3.17 列出 17 个路由级页面/视图；§3.18 是应用壳层，不是独立路由视图。报告摘要称“18 个视图 + 7 个对话框”。

**影响**
后续“18 页 × 8 状态”“18 页 × 2 主题”可能把应用壳层误当页面，或把登录页、对话框重复计数，造成验收矩阵口径漂移。

**修订要求**
将统计拆开并固定口径：
- 17 个路由级视图（以报告实际路由表为准）；
- 1 个跨页应用壳层；
- 7 个静态/动态对话框入口（逐个列名）；
- 状态矩阵只对适用的数据视图执行；登录、壳层、纯对话框按适用性标 N/A 并说明理由。
全篇统一“页面/路由视图/壳层/对话框”术语。

### UIREV-05｜P2：图标“全部 emoji 清零”与规范允许用户自定义分类图标冲突

**证据**
- 视觉规范 §2 明确写明：业务分类可保留用户自定义图标，不强制替换数据内容。
- 报告 §7 的 UI-DESIGN-03 却要求“22+4 种 emoji 全部替换为 Lucide，grep emoji 范围应为 0”。

**影响**
执行者可能把用户数据中的分类 emoji 也替换/清除，违反规范的兼容要求；对所有文本做 emoji grep 也不是有效的 UI 图标验收。

**修订要求**
把替换范围限定为应用导航、按钮、操作和状态提示中的装饰性/功能性图标。用户自定义分类图标、交易备注/商户文本和业务数据不得批量替换。验收应基于 DOM/组件图标来源清单，而不是全仓 emoji 数量必须为零。

### UIREV-06｜P2：原生选择器/日期控件不得以“数量归零”作为无条件验收

**证据**
报告 §7 UI-DESIGN-03 要求全站 `<select>` 与 `<input type=date>` 数量为 0，仅允许无障碍降级路径说明。

**影响**
自定义控件并不天然优于原生控件。若没有键盘、屏幕阅读器、焦点、移动端系统选择器、日期本地化和弹层边界的等价验收，强制清零可能降低可访问性和移动端可用性。

**修订要求**
按控件场景逐个决策：确需自定义时，必须证明键盘/屏幕阅读器/焦点管理/触控/本地化行为；适合保留原生控件的场景允许保留，并记录原因。验收“交互一致且可访问”，不验收标签数量归零。

## 3. 已确认正确、应保留的内容

1. **业务基线声明正确**：报告明确以 PR #3 的 `4318fd6` 为当前修复基线，并指出 main 尚缺四处修复，提醒 UI 改造不能误从旧 main 开始。
2. **安全边界正确**：强调现有 `app.js` 不使用 `innerHTML`，组件工厂必须继续通过 DOM API / `textContent` 构造，禁止字符串拼接 HTML。
3. **既有功能保护充分**：对分类 `catType` 过滤、交易 `clientUuid` 幂等、`baseVersion` 并发保护、编辑时交易类型不可改、成员邀请角色门控、投资独立页、D-4/D-8 不顺手实现等保留项记录较完整。
4. **入口问题值得纳入改造**：分类管理缺入口、手机设置/退出登录不可达、“我的”桌面端无入口、账本导航链接隐藏、设置页 `[data-nav]` 死选择器等均应保留为待验证/待修复项。
5. **首页净资产问题识别正确**：账户余额合计与投资页 `/net-worth` 口径不能混称净资产。建议优先复用现有权威 `GET /net-worth` 响应统一展示；若字段不满足，应先登记 Owner 决策，不得自行改会计口径或新增 API。
6. **R0/PWA 门禁意识正确**：报告承认没有浏览器/真机/运行时证据，也明确 Offline/Syncing/Conflict 不能伪造 PASS。此边界必须保留。
