## 二、必须修订的问题

### R18-RV-01：§8.2 阶段2与§3.1要素10.3/10.4冲突

**证据：**
- §3.1 要素10.3要求：在未获正式授权修改 C 套件状态/统计前，I-BOOKS-09 走独立追踪；与 228 项物理分离；不修改 `controls.json`、`c-controls.js`、runner，也不改 `164/4/59/1/228`。
- §3.1 要素10.4要求：G-2 完成后，先走正式测试清单修订授权，再运行真实断言，最后由 Owner/PM 决定是否纳入 C 套件统计。
- 但§8.2阶段2仍写：`BLOCKER-04 → 授权后改 runner 真实断言（不碰计数/状态）+ I-BOOKS-09 按 #navBooks 定义补真实断言`。

**问题：**
阶段2没有说明 I-BOOKS-09 的断言究竟放在 C runner 还是独立追踪通道。若放入 `c-controls.js`，就违反10.3的物理分离；若不放入，则阶段2的“补真实断言”没有指定执行载体。并且阶段2没有把 G-2 完成和测试清单修订授权列为 I-BOOKS-09 的前置条件。

**修订要求：**
1. 把 BLOCKER-04 的四条 FAIL runner 整改，与 I-BOOKS-09 过渡验收明确拆成两条工作线。
2. 阶段2对 I-BOOKS-09 只能建立独立追踪方案/独立执行载体，不得把它加入现有 C runner 或改变 C 套件统计。
3. 若尚无独立脚本/探针，明确先列为“待独立执行载体授权/建立”，不得宣称已完成真实断言。
4. I-BOOKS-09 纳入 C 套件的动作必须等 G-2 完成、测试清单修订获授权之后再执行。

### R18-RV-02：§3.1要素10.2声称“真实断言已就位”，但本轮没有任何断言执行载体

**证据：**
- 要素10.2要求过渡期记录“真实断言已就位但因产品实现缺口未通过”。
- 要素10.3同时禁止修改 `controls.json`、`c-controls.js`、runner。
- §9.2声明本轮没有修改测试判定、runner或fixture。
- 本轮只修改任务单文档，没有新增独立脚本、临时探针或人工验收记录模板。

**问题：**
当前已知 `c-controls.js:163` 仍是硬编码 PASS。没有独立执行载体或执行记录，就不能称“真实断言已就位”；最多只能说“真实断言方案已定义，尚未执行/尚无独立执行载体”。若G-2未完成前要记录预期失败，必须先说明由什么机制执行并保存结果。

**修订要求：**
把状态分成至少三种：
- **方案已定义**：本任务单已列出四项判据。
- **执行载体已建立并获授权**：独立脚本/只读探针或其他经授权的检查方式已存在。
- **真实检查已执行**：有时间、commit、viewport、DOM可见性、点击结果、实际 hash、截图/诊断等证据。

在没有第二、第三种证据前，禁止使用“真实断言已就位”“真实断言已运行”或“预期失败已记录”等完成态措辞。

### R18-RV-03：独立过渡追踪缺少最小证据记录契约

**证据：**
- 要素10.3只说“逐次记录真实断言运行结果、失败诊断与截图留痕”。
- 没有规定每次记录的必填字段、文件位置、执行方式、如何确认是当前 HEAD 的结果。
- §8.2阶段3只列一般性第三方复核，没有明确 I-BOOKS-09 独立追踪记录的验收格式。

**问题：**
“独立追踪”目前只是原则，没有可重复执行和审计的记录格式，容易出现只写一行“预期失败”却没有浏览器证据的情况。

**修订要求：**
至少定义每次记录字段：
- 追踪ID：`I-BOOKS-09-TRANSITION`
- 执行时间与执行者
- 仓库分支、完整 commit SHA
- 浏览器/Playwright版本（如适用）
- viewport
- `#navBooks` DOM存在性
- `hidden` class / computed visibility / bounding box
- enabled/可交互状态
- 实际点击是否执行；若因 hidden 无法点击，记录具体错误
- 点击前后 hash
- 截图与诊断文件路径
- 结论：未执行 / 预期失败 / 通过
- 是否属于 C 套件统计：固定为“否（过渡期）”

如采用独立 Playwright 脚本，脚本应放在独立目录并与 C 套件隔离；若采用人工浏览器检查，也必须提供明确步骤和证据保存规范。不得将其伪装成 C 套件运行结果。

### R18-RV-04：I-BOOKS-09 的 `#navBooks → #books` 不等于已验收“直接切换目标账本”

**证据：**
- controls.json 对 I-BOOKS-09 的定义是顶栏“账本”入口，点击后 `hash=#books`。
- §3.1要素10.1据此要求验证 DOM 存在、可见、可点击、hash 跳转。
- §5.2对 G-2 的验收描述还包含“可直接选目标账本”。

**问题：**
点击顶栏入口后进入 `#books` 账本列表，只能证明入口可用并导航到列表；它本身不证明用户能在顶栏直接选择目标账本，也不证明目标账本切换后路由、数据上下文正确。两者可能是不同验收层级。

**修订要求：**
明确拆分：
- I-BOOKS-09：严格按现有 fixture，只验收 `#navBooks` 入口与 `hash=#books` 导航。
- G-2：按 D-3 产品决策验收顶栏账本切换能力；若产品方案要求直接选择目标账本，应另验收选择目标账本后的 hash/账本ID/页面数据上下文一致性。
不得把 I-BOOKS-09 通过等同于 G-2 全部通过，也不得借 I-BOOKS-09 的 PASS 关闭 G-2。
