## 1. 术语表

| 术语 | 含义 |
|---|---|
| 账本（Book） | 一套独立的账，拥有独立的账户、分类、交易；如"家庭公共账""个人私账" |
| 资金账户（Account） | 实际存放资金的载体，如储蓄卡、现金、信用卡、电子钱包、投资账户 |
| 支付渠道（Payment Channel） | 一笔付款的"走账方式"，如微信、支付宝、云闪付、POS；与资金账户是两个维度 |
| 交易（Transaction） | 一笔收入、支出或转账记录 |
| 标的（Instrument） | 可被投资/持有的金融工具，如股票、基金、债券、黄金 |
| 持仓（Holding） | 某投资账户对某标的的持有数量与成本 |
| OCR | 光学字符识别，把截图/图片中的文字识别为文本 |
| 端侧 | 用户自己的设备（手机/电脑），不依赖服务器完成的计算 |
| 信封预算 | 把每月预算按类别"分装信封"，花完即止的预算管理方式 |
| NAS | 家庭网络附加存储，用户自有的常开服务器设备 |
| DDNS | 动态域名解析，家庭宽带 IP 变化时仍能用固定域名访问 |

## 2. 产品概述

### 2.1 背景与问题

**背景。** 目标用户（技术爱好者家庭）有强烈的家庭财务记录与资产盘点需求，但现有方案存在以下痛点：

1. **录入繁琐**：手动逐笔记账坚持成本高；主流 App 的"截图自动记账"能力依赖其云端，隐私不可控。
2. **数据不在自己手里**：商业记账软件存在停服、数据导出受限、广告与变现等问题。
3. **多渠道账单重复且混乱**：同一笔消费可能在微信、支付宝、信用卡账单中同时出现，直接合并会重复计算。
4. **家庭共享能力弱**：夫妻共同记账、多账本（公共账 + 各自私账）、可见性控制缺乏灵活组合。
5. **资产与负债割裂**：现金、信用卡、多个券商账户、基金、房产、汽车、黄金等缺乏统一的家庭净资产视图。

### 2.2 产品定位

**一句话定位：** 一款自托管（部署在家庭 NAS/Docker）的、以"截图 → 本地识别 → 人工确认 → 家庭共享"为核心体验的家庭智能记账与资产管理系统。

**核心特征：**
- 数据自主：数据存储在用户自有设备，支持完整导出。
- 隐私优先：识别尽量在端侧完成，图片不上传；云端仅作可选兜底。
- 多端协同：Windows / Android / iOS 客户端 + Web 快捷浏览。
- 家庭共享：多账本、多成员、可见性可控。
- 资产全景：日常收支与投资、实物资产、负债统一到净资产。

### 2.3 产品目标与成功指标

**产品目标（按优先级）：**

1. 让用户能以最低成本（截图确认）完成日常记账，并长期坚持。
2. 让一个家庭能在统一视图中掌握收支与净资产。
3. 让用户对数据拥有完全控制权（自有部署、可导出、可备份）。

**成功指标（建议，需上线后校准）：**

| 指标 | 目标口径 | 类型 |
|---|---|---|
| 截图识别确认率 | 识别后用户仅做少量修改即确认的比例 ≥ 80% | 【假设】 |
| 周活跃记账天数 | 核心用户每周 ≥ 4 天有记账行为 | 【假设】 |
| 识别响应 | 截图到确认弹窗弹出 < 3 秒（OCR 耗时，不含人工操作） | 【假设】 |
| 录入耗时 | 完整一笔（触发到入账，含人工确认）≤ 15 秒 | 【假设】 |
| 数据可靠性 | 自动备份成功率 ≥ 99%，无数据丢失 | 质量目标 |
| 资源占用 | 后端常驻内存 < 150 MB（适配低功耗 NAS） | 质量目标 |

> 说明：上述含具体数值的指标为产品初始目标，非既成事实；上线后需依据真实数据校准。

**度量方法（如何采集，不依赖外部埋点）：**

| 指标 | 采集方式 | 口径 |
|---|---|---|
| 截图识别确认率 | 客户端本地统计：识别后"未改任何字段直接确认"的笔数 ÷ 识别总笔数 | 按周汇总，仅本地统计，不上传 |
| 周活跃记账天数 | 按 `transactions.tx_time` 统计每个用户当天有记录的去重天数 | 自然周（周一至周日） |
| 识别响应 | 客户端记录"触发→弹窗"时间戳差值 | 取 P95，而非平均值 |
| 录入耗时 | 客户端记录"触发→入账成功"时间戳差值 | 取 P95 |
| 数据可靠性 | 备份任务的成功/失败计数 + 定期校验备份可恢复 | 按月统计成功率 |
| 资源占用 | 容器/进程内存采样（如每 5 分钟） | 取峰值与 P95 |

> 隐私说明：以上使用类指标默认只在**用户本地/自有服务器**统计，用于自用校准，不向任何第三方上报。

### 2.4 非目标（本期明确不追求）

- 不做银行/支付平台的**自动抓取账单**（合规风险高、维护成本高）。
- 不做**多人协作的复杂审批流**、对公财务、税务申报。
- 不做社交、内容社区、理财推荐/交易撮合。
- 不做跨家庭的公开账本市场。
- 不追求 iOS 全局后台自动截图（系统沙盒不允许，上架必拒）。

### 2.5 用户画像

**画像一：技术爱好者户主（主要使用者）**
- 有编程/折腾能力，拥有 NAS 或常开设备，能完成 Docker 部署。
- 关注隐私与数据自主，对资源占用敏感。
- 承担系统搭建、成员管理、资产盘点。

**画像二：家庭成员（配偶）**
- 技术能力一般，主要在手机上快速记账、查看公共账与家庭报表。
- 希望操作简单，不关心部署与配置。

**画像三（预留）：扩展家庭成员**
- 如父母、子女，未来加入特定账本，权限受限。

### 2.6 核心使用场景

1. **快速记一笔**：手机支付后截图，系统端侧识别，弹出预填确认框，用户确认即入账。
2. **手动记账**：现金消费或识别失败时，手动选择分类、账户、金额录入。
3. **信用卡还款**：把储蓄卡扣款还信用卡，记为"转账"，不重复计入支出。
4. **月度复盘**：查看本月收支、分类占比、预算执行，导出账单存档。
5. **家庭协作**：夫妻各自记公共账，默认互看；个人私账可隐藏。
6. **资产盘点**：录入各券商持仓、基金、房产、车辆、黄金，查看家庭净资产；未来自动更新行情。

### 3.2 MVP（v0.1）范围

**MVP 必须形成最小闭环：** 注册登录 → 配置账户/分类 → 手动或截图记一笔 → 首页与报表可见 → 可导出。

**MVP 包含：**
- 注册、登录、长期 Token
- 资金账户（含信用卡、电子钱包）、两级分类
- 手动记账（收入/支出/转账）
- 截图识别（端侧 OCR + 规则 + 人工确认）
- 首页账单、交易详情/编辑/删除
- 基础报表（月度收支、分类占比）
- CSV/JSON 导出
- **多账本**：默认创建"家庭公共账本"，可新建"个人私账"并切换；成员（2 人起步）、角色、可见性开关
- 投资/资产模块的**数据骨架与手动录入**（不做自动行情）

**MVP 可砍但必须保留扩展骨架的部分：**
- 自动行情、预算结转、xlsx/PDF 导出、多到 5 人以上的完整交互（数据结构先行）。

## 4. 功能需求详述

> 每项功能按"触发 → 系统行为 → 用户可见结果 → 异常处理"描述，验收见第 10 章。

### 4.1 注册与登录

- 支持用户名 + 密码注册/登录；密码用 bcrypt/argon2 哈希存储（算法自带随机盐，不可逆）。
- 登录成功后下发访问令牌；支持长期 API Token（用于客户端/快捷指令）。
- 支持多端同时在线，可查看与撤销会话。
- 首次注册引导：创建默认账本、默认账户与默认分类。
- 异常：密码错误、用户名重复、Token 失效需明确提示并引导重新登录。

### 4.2 首页与账单

- 顶部展示本月支出、本月收入、结余。
- 账单按日期分组，每条显示分类图标、商户/备注、金额、账户与渠道。
- 支持按时间、账户、分类、类型、关键词筛选。
- 提供"记一笔"入口（截图识别 / 手动记账）。
- 数据更新后，首页概览与列表实时联动。

### 4.3 记账（核心）

#### 4.3.1 手动记账

- 类型：收入、支出、转账。
- 必填：金额、账户、分类（支出/收入）、时间；选填：渠道、商户、备注、标签。
- 转账：选择转出账户、转入账户、金额与发生时间；作为同一笔业务原子提交，不计入收支。余额按资产/负债符号变化，使两侧净资产贡献相抵；例如储蓄卡还信用卡时，两边存储余额都减少。
- 创建交易（含转账与离线补传）必须携带稳定的客户端操作键；同键同内容返回原交易结果，同键改内容提示冲突，不能静默当成新的记账或空成功。技术入口见《落地方案》与《转账入口裁决》。
- 金额输入支持小数，存储统一为最小货币单位（分），避免浮点误差。

#### 4.3.2 截图识别记账（核心卖点）

- 入口：客户端"截图记账"，或从系统分享/快捷指令把截图送入。
- 流程（识别三级漏斗）：
  1. **端侧 OCR**：在设备本地识别截图文字（图片不上传）。
  2. **端侧规则解析**：用可更新的规则（微信/支付宝等）从文本提取金额、商户、时间、渠道等。
  3. **云端 LLM 兜底（可选）**：规则无法解析时，仅把 OCR 文本（不含图片）发送给大模型解析。
- 结果进入**人工确认表单**，预填字段，用户可修改后确认。
- **任何识别结果都必须经人工确认后才入账**，不允许自动入账。
- 异常：识别为空、字段缺失、解析失败时，回退到手动记账并保留文本。

#### 4.3.3 支付渠道与资金账户（解决重复混乱）

- 一笔交易同时记录两个维度：
  - **资金账户**：钱实际从哪出（如"招行信用卡""微信零钱"）。
  - **支付渠道**：通过什么方式付（微信/支付宝/云闪付/POS/直接）。
- 典型场景：
  - 用微信绑定的信用卡支付 → 账户=信用卡，渠道=微信。
  - 用支付宝绑定的同一张信用卡支付 → 账户=信用卡，渠道=支付宝。
  - 信用卡还款（储蓄卡→信用卡）→ 转账，不产生新支出。
- 这样月度账单按"资金账户"与"交易"统计，不会因微信、支付宝、信用卡各出一份而重复。

### 4.4 交易管理

- 点击交易进入详情，可编辑全部字段、可删除。
- 删除需二次确认；删除后账户余额、报表、预算联动回滚。
- 转账删除需同时回滚两个账户。
- 支持软删除（数据可恢复/审计），具体保留策略见第 6 章。

### 4.5 账户管理

- 账户分类（15 类，见第 6 章）：资产端（现金、活期、定期、电子钱包、投资、实物、保险、其他、应收），负债端（信用卡、消费贷、房贷、车贷、其他借款、应付）。
- 账户属性：名称、分类、币种、初始余额、是否计入净资产、是否启用、备注。
- 支持多币种（MVP 以 CNY 为主，结构预留外币）。
- 账户余额由交易实时计算，也支持期初余额。

### 4.6 分类管理

- 两级分类：大类下挂小类（如"旅游"下"旅游交通/旅游住宿"）。
- 支持新增、编辑、删除、（建议）排序。
- 分类被交易引用时删除需处理（禁止删除或迁移到"其他"）。
- 数据结构支持未来扩展为多级分类。

### 4.7 预算

- 采用信封式：可设置总预算与分类月度预算。
- 展示预算进度：已用/总额、剩余、百分比。
- 状态：正常、接近（建议阈值 80%）、超支（红色）。
- 数据结构预留"是否结转上月余额"字段，MVP 不实现结转。
- 【决策】预算周期：MVP 固定自然月，自定义周期列为 P2（见 §12 第 1 项）。

### 4.8 报表

- 月度收支趋势（折线/柱状）。
- 支出分类占比（饼图）。
- 支持切换时间范围、账本、账户范围。
- 报表随数据实时更新。

### 4.9 导出

- 格式：CSV（带 UTF-8 BOM，Excel 可直接打开）、JSON。
- 支持按时间、账户、分类、类型、渠道筛选，支持字段勾选。
- 导出前可预览。
- 后续版本：xlsx、PDF。

### 4.10 家庭与共享

- 支持多个独立账本；每个账本有独立成员、账户、分类、交易。
- 成员角色：owner / admin / member（见第 7 章）。
- 可见性：**成员默认互看账本内容，提供开关可关闭**；个人私账可设为仅自己可见。
- 支持邀请成员（邀请链接/码）、移除成员、角色变更。
- 规模：2 人起步，数据结构与交互支持扩展到 5 人或更多。

### 4.11 投资与资产

- 资产总览：总资产、总负债、净资产，按分类汇总。
- 投资账户：券商/基金账户，包含现金与持仓市值。
- 标的库：股票、基金、债券、黄金等，可新增。
- 持仓：标的、数量、成本、最新价、市值、浮动盈亏。
- 实物资产：房产、汽车、实物黄金等，记录估值。
- MVP：建表 + 手动录入行情/估值；v0.3：自动行情；v0.4：完整资产合计。
- 【决策】自动行情：MVP 不做自动行情，仅手动录入与导入（见 §12 第 3 项）。

### 4.12 我的 / 设置

- 个人资料、账号安全、密码修改。
- 长期 API Token 管理（生成、查看、撤销）。
- 服务器信息、数据备份与恢复入口。
- （管理员）系统级设置、外部 LLM 配置、备份策略。

## 5. 核心业务流程

### 5.1 截图识别记账流程

```
用户截图/分享图片
   │
   ▼
端侧 OCR（图片不出设备）
   │  文本
   ▼
端侧规则解析（微信/支付宝…）
   │  成功 ──► 预填确认框
   │  失败
   ▼
云端 LLM 兜底（仅传文本，可开关）
   │
   ▼
人工确认（可修改任意字段）
   │  确认
   ▼
写入交易 → 更新账户余额 → 首页/报表/预算/资产联动
```

### 5.2 多端形态与 OCR 分工

| 端 | 形态 | OCR 能力 |
|---|---|---|
| Android | Flutter 客户端 | 端侧离线 OCR（中文模型） |
| iOS | Flutter 客户端 | 经"快捷指令 + 系统 Vision"识别，回传 App |
| Windows | Flutter 客户端 | 系统 OCR / 端侧 OCR |
| Web | 浏览器，go:embed 托管 | 不做 OCR，用于浏览与编辑 |

### 5.3 转账与还款

- 储蓄卡 → 信用卡还款：记为转账，两账户余额变化，不影响收支统计。
- 信用消费：当时记一笔支出（账户为信用卡），还款时仅转账，不重复。

## 6. 数据模型（关键）

### 6.1 实体关系概览

```
users ──< book_members >── books
books ──< accounts
books ──< categories (自关联 parent_id)
books ──< transactions >── accounts (资金账户)
transactions ──< transaction_tag_index >── tags
accounts(投资类) ──< holdings >── instruments
instruments ──< instrument_prices
books ──< budgets
users ──< auth_tokens
```

### 6.2 关键表（字段级摘要）

| 表 | 关键字段 | 说明 |
|---|---|---|
| users | id, username, email(可选), password_hash, created_at | 用户 |
| books | id, name, owner_id, visibility, created_at | 账本 |
| book_versions | book_id, version | 账本级全局版本计数器（每写事务 +1） |
| book_members | id, book_id, user_id, role, can_view_others(预留) | 成员与角色 |
| accounts | id, book_id, parent_id(分组), name, category, currency, balance, sync_version, deleted_at | 资金账户 |
| categories | id, book_id, parent_id, name, sort_order, sync_version, deleted_at | 分类（两级） |
| transactions | id, book_id, type, account_id, to_account_id, amount, category_id, payment_channel, merchant, note, transaction_time, related_id, client_uuid, sync_version, deleted_at | 交易 |
| tags / transaction_tag_index | id, name / transaction_id, tag_id | 标签 |
| auth_tokens | id, user_id, token, name, expires_at | API Token |
| instruments | id, type, code, name, currency, exchange | 标的 |
| holdings | id, account_id, instrument_id, quantity, cost | 持仓 |
| instrument_prices | id, instrument_id, price, price_date | 行情历史 |
| budgets | id, book_id, category_id, amount, period, rollover | 预算 |

### 6.3 关键规则

- **全局版本号（增量同步核心）**：每个账本在 `book_versions` 维护单调递增版本；写事务内先 +1 取得 `newVersion`，再写入实体的 `sync_version`；客户端按 `afterVersion` 拉取 `sync_version` 更大的变更。
- **金额**：以整数（分）存储，避免浮点误差；展示时换算为元并千分位。
- **高精度数量/价格**：持仓数量、证券价格用字符串存储，运算走十进制库（如 shopspring/decimal），禁止 float。
- **软删除**：核心表含 deleted_at，支持误删恢复与审计。
- **转账成对**：通过 related_id 关联转出/转入两条记录，保证可追溯。
- **分类层级**：parent_id=0 表示大类，结构上支持未来多级。
- **账户分类（15 类）**：
  - 资产：1 现金（含外币）、2 活期、3 定期（预留）、4 电子钱包、5 投资账户、6 实物资产、7 保险（预留）、8 其他、9 应收（预留）
  - 负债：10 信用卡、11 信用消费贷、12 房贷、13 车贷、14 其他借款、15 应付（预留）

## 7. 角色与权限

### 7.1 角色定义

| 角色 | 说明 |
|---|---|
| owner | 账本所有者，最高权限，不可被他人移除，唯一 |
| admin | 管理员，可管理成员、分类、账户、设置 |
| member | 普通成员，可记账、查看（受可见性限制）、管理本人记录 |

### 7.2 权限矩阵（建议）

| 操作 | owner | admin | member |
|---|---|---|---|
| 记账/编辑本人记录 | ✓ | ✓ | ✓ |
| 编辑/删除他人记录 | ✓ | ✓ | ✗（member 仅可编辑/删除本人记录） |
| 管理账户/分类 | ✓ | ✓ | 部分（建议仅本人） |
| 邀请/移除成员 | ✓ | ✓ | ✗ |
| 变更角色 | ✓ | ✓ | ✗ |
| 账本可见性开关 | ✓ | ✓ | ✗ |
| 删除/转让账本 | ✓ | ✗ | ✗ |
| 系统设置/备份 | ✓ | ✓（建议受限） | ✗ |

### 7.3 可见性规则

- 账本默认成员互看；提供开关关闭后，成员仅看本人记录。
- 个人私账可设为仅自己可见。
- 可见性判定在服务端执行，不能仅依赖前端隐藏。
- 【粒度】MVP 启用**账本级**开关（`books.members_can_view_others`）；`book_members.can_view_others` 字段作为**成员级覆盖**预留（未来可单独设定某人是否可见，MVP 不启用）。

## 8. 非功能需求

### 8.1 性能

- 后端常驻内存目标 < 150 MB；适配低功耗 NAS。
- 常规列表/报表查询响应建议 < 500 ms（本地网络）。
- 数据库 SQLite 起步，数据结构预留迁移到 PostgreSQL/MySQL。

### 8.2 安全与隐私

- 全站 HTTPS（外网访问经 Caddy 自动证书）。
- 密码用 bcrypt/argon2 哈希（算法自带盐，不另设 salt 列）；Token 仅存哈希/可撤销。
- 识别默认端侧完成；云端兜底仅传文本，且提供开关。
- 敏感字段（账户、资产）访问受角色与可见性控制。
- 不在日志中记录密码、完整 Token 等敏感信息。

### 8.3 可靠性与备份

- 支持数据库与文件的定期备份（建议挂载到 NAS 存储）。
- 关键写操作使用事务（转账、记账）。
- 提供备份恢复说明与校验。

### 8.4 兼容性

- 客户端覆盖 Windows、Android、iOS；Web 覆盖主流浏览器。
- 各端分辨率与横竖屏适配（移动端优先）。

### 8.5 部署与运维

- 以 Docker 镜像交付，支持 docker-compose 一键启动。
- 外网访问：Caddy 反代 + DDNS + 自动 HTTPS。
- 数据卷与配置文件持久化，升级不丢数据。
- 【加固】**备份必须原子包含 WAL**：仅复制 `*.db` 而漏掉 `-wal`/`-shm` 会丢失尚未 checkpoint 的最近事务。备份须用 `sqlite3 .backup` 或 `VACUUM INTO`，或先 `PRAGMA wal_checkpoint(TRUNCATE)` 再整目录复制（见《落地方案》§8.3）。
- 【加固】**优雅关机必须 checkpoint**：容器停止时须在 `stop_grace_period`（建议 ≥30s）内处理 SIGTERM → 关闭数据库引擎触发 WAL checkpoint；禁止直接 SIGKILL，否则每次重启都残留大 WAL 文件。
- 【加固】**`synchronous=FULL` 不替代备份**：FULL 只解决掉电丢失已提交事务，挡不住磁盘/文件系统故障与误删。须保留每日备份（§12 决策#5）并**定期做恢复演练**（见 §10.9）。
- 【加固】**恢复后递增 `restore_epoch`**：该标记独立于数据库、不随备份恢复；客户端发现世代变化即全量重建并核对离线队列，防止旧缓存覆盖恢复后的数据（见《落地方案》§8.3）。

## 9. 异常与边界场景

1. **识别失败/为空**：回退手动记账，保留 OCR 文本辅助填写。
2. **重复提交/双击**：提交按钮防重，必要时幂等处理。
3. **转账部分失败**：事务保证两账户同时成功或同时回滚。
4. **删除被引用分类/账户**：禁止直接删除或引导迁移，避免历史数据失真。
5. **多端并发编辑同一笔**：【决策】服务端为权威（最后修改 + 版本号）；端侧提交时若该实体已被他人更新（`sync_version` 更大），返回冲突，由用户选择覆盖 / 放弃 / 另存副本。
6. **跨币种交易**：MVP 以本币为主，跨币种记录汇率（预留）。
7. **网络中断**：【决策】客户端本地缓存待同步队列（带 `clientUuid` 幂等），联网后先 push 再 pull 补漏。
8. **行情获取失败**：保留上次价格并标注更新时间，不影响手动数据。

## 10. 验收标准（核心）

> 采用"给定—当—则"形式，覆盖成功与关键失败场景。

### 10.1 手动记账

- 给定已登录且存在账户与分类；当提交一笔支出；则列表顶部出现该笔、账户余额减少、本月支出增加、报表更新。
- 当金额为空或非法；则无法提交并提示。

### 10.2 截图识别

- 给定一张微信支付截图；当端侧识别成功；则确认框预填金额/商户/时间/渠道；确认后正确入账。
- 当规则无法解析；则进入云端兜底或回退手动，且不自动入账。

### 10.3 转账/还款

- 给定储蓄卡与正欠款信用卡；当做一笔还款转账；则储蓄余额与信用卡欠款都减少，两侧净资产贡献相抵，净资产及收支统计不变。
- 当转账删除；则两账户余额同时回滚。

### 10.4 支付渠道不重复

- 给定多笔通过微信/支付宝走同一信用卡的消费；当查看月度账单；则每笔仅计一次，账户为信用卡，渠道分别标记，不出现重复。

### 10.5 预算

- 给定某分类预算；当该分类支出达到阈值；则状态切换为接近/超支并颜色提示。

### 10.6 导出

- 给定筛选条件；当导出 CSV；则文件可被 Excel 正确打开（无乱码），内容与筛选一致。

### 10.7 家庭与可见性

- 给定两名成员；当关闭互看开关；则成员仅能看到本人记录，服务端同样生效。

### 10.8 投资与资产

- 给定投资账户与持仓；当手动录入最新价；则市值与盈亏正确计算；净资产汇总包含实物与负债。

### 10.9 备份恢复与审计

- 给定一份 N 天前的备份；当在新实例执行恢复；则记录数与校验和一致、`restore_epoch` 递增、客户端全量重建后可正常读写（恢复演练）。
- 给定一笔转账；当删除该笔转账；则两条记录同时进入回收站、两侧余额同时回滚、版本号统一递增；当恢复该笔；则两侧余额同时回滚，且净资产与删除前一致。
- 给定任一写操作；当执行后查询审计日志；则可查到操作者、时间、实体与变更前后状态。

## 12. 待确认问题（评审重点）

> 评审结论（v1.5）：以下原待确认项已根据多 AI 评审与快速原型视角逐一拍板。除 §12.1 标注【待确认】的技术项外，其余已转为【决策】。已决策（不再列为待确认）：**多端并发冲突**采用"服务端权威 + 版本号，冲突时用户选覆盖/放弃/另存"；**离线同步**采用"本地队列 + clientUuid 幂等，联网后 push 再 pull"。

1. 【决策】预算周期：MVP 固定为自然月；自定义周期（按周/按薪资日等）列为 P2 后续，不在首版实现。
2. 【决策】编辑/删除他人记录：member 仅可编辑/删除本人记录；owner 与 admin 可管理本账本全部记录（最小权限原则，见 §7.2 权限矩阵）。
3. 【决策】自动行情：MVP 不做自动行情，仅支持手动录入与导入；若后续引入，以手动价格优先、公开 API 为源、可刷新。
4. 【决策】多币种：MVP 仅支持 CNY，不做隐式换汇（与《转账入口裁决》GPT-ADR01 一致）；多币种为 P2。
5. 【决策】备份：每日生成 1 份备份，滚动保留最近 7 份；结合 §6 持久性策略（synchronous=FULL）确保可恢复。
6. 【决策】成员规模：MVP 账本成员上限 20 人（家庭/小圈子足够），不做硬卡 5 人限制。
7. 【决策】云端 LLM 兜底：默认关闭，仅启用本地 OCR + 规则识别；开启需用户明示同意，并在客户端与服务端双侧提供开关，对含账户/姓名等敏感文本做脱敏，配置超时与额度限制。
8. 【决策】账本转让/成员退出：成员退出为软删关系、保留其历史记录（不可篡改审计）；账本 owner 转让需新 owner 显式接受后生效。

### 12.1 技术待确认（GPT 评审补充）

以下为 GPT 评审在 `gpt/FastLedger-review-b874146.md` 单列、且当前仓库无法确认行为的技术开放项，仍记为【待确认】；其中“云端兜底完整开关”已由第 7 项【决策】覆盖。

- 【待确认】权限变化与本地缓存重建：互看从开变关、成员被移除/重新加入时，离线缓存、已同步版本与新可见范围如何重建；历史已看/已导出数据服务端无法收回，需写明隐私边界。
- 【待确认】实例管理员与账本 owner 边界：明确谁可下载整库备份、修改 LLM 密钥；普通账本 owner 不等于实例管理员，不默认获得所有私账。
- 【待确认】关闭公开注册后的成员入户：`EBK_ENABLE_REGISTER=false` 时，邀请链接是否可注册、邀请码有效期/单次使用/角色绑定/限流如何定义。
- 【决策】断电持久性：采用 `synchronous=FULL`（与 §12 决策#5 一致）；已同步《新手开发完整指南》§22.4 的 initDB DSN 与《落地方案》§6.1。理由：家庭 NAS 单机、日写量极小，FULL 的 fsync 开销可忽略；NORMAL 在掉电时可能丢失最近已提交事务，与"无数据丢失"质量目标冲突，故不采用"书面豁免"。配套：每日备份 + 恢复演练（§11）。
- 【决策】删除恢复与审计：软删除不等于审计。owner 裁决采用以下设计（回收站保留 30 天、审计保留 1 年）：
  1. **回收站与保留期**：软删字段（`deleted_at`）已有，需补"回收站"入口；**保留 30 天**（配置项 `EBK_RECYCLE_TTL_DAYS`，默认 30），到期硬清除。删除须在**同一事务**内完成：置 `deleted_at` → 版本号 +1（`VersionRepo.Next`）→ 写 `sync_version` → 写审计。
  2. **转账双边、禁止单边**：转账为两条 transaction（`related_id` 互指），删除/恢复必须以**整笔**为单位（用分组键 `transfer_group_id` 或复用 `related_id` 绑定）；两侧余额回滚在同一事务内完成，版本号统一 +1，并写幂等回执。不得存在只处理单条的路径。
  3. **审计日志独立成表（append-only）**：新增 `audit_logs(id, book_id, actor_uid, action, entity_type, entity_id, before_json, at, source)`，覆盖 create/update/delete/restore/登录/权限变更/备份恢复；须记录**变更前后状态与操作者**（软删仅有 `deleted_at`，无法回答"谁删的、删前是什么"）。仓库层禁止对该表 UPDATE/DELETE，定期归档；**保留 1 年**或按容量滚动。此为实现 §12 决策#8"不可篡改审计"的基础。
  4. **旧离线数据回流**：客户端离线队列可能在实体被删后 push 上修改。服务端比对 `sync_version`，目标已删则返回明确错误（409 + `ENTITY_DELETED`），客户端丢弃该队列项或转"冲突/另存"；**绝不静默复活已删数据**。`restore_epoch` 不符则强制全量重建。
  5. **恢复演练纳入验收**：见 §10.9。
  6. **入口对称**：新增统一的 `TxService.Delete/Restore`（或 `SetDeleted`），与 `TxService.Create` 对称，复用 `VersionSource` + 幂等回执 + 单一事务边界，避免重蹈"双入口"覆辙（参见《转账入口裁决》GPT-ADR01）。
