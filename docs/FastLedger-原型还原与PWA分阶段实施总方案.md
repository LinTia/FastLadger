# FastLedger 原型还原与手机 PWA 分阶段实施总方案

> 文档性质：跨 AI / 开发者的实施总控方案。把当前 Web 实现向产品原型收敛、移动端完整体验、PWA 完整离线和本地备份恢复串成可验收的路线。
>
> 状态：实施规划，**不是代码完成报告**。本文件不授权 AI 自行改变产品语义，也不替代 PRD、落地方案、枚举字典和专项指导书。
>
> 编制日期：2026-11-04。适用仓库：`LinTia/FastLadger`，以执行时 `main` 最新提交为准。

## 1. 目标与总原则

### 1.1 最终目标

1. Web 的页面结构、导航、关键交互和视觉表现与经 Owner 确认的原型基线一致，不再以“能访问 API / 有同名页面”冒充原型还原。
2. 桌面 Web 与手机端形成一致的业务能力；手机端是完整移动端，不是把桌面表格缩窄。
3. 手机端可安装为 PWA；首次在线完成缓存后，可离线查看已缓存数据、执行明确允许的离线记账操作、分析本机数据。
4. 离线操作可靠持久化，联网后按既有幂等、版本、权限、冲突和恢复世代契约同步；不重复、不静默覆盖、不复活已删除数据。
5. 用户可离线导出加密本地备份并在本机校验恢复；本地恢复默认不向服务端推送。
6. Flutter 原生端继续承担浏览器无法可靠提供的系统级能力（如 Windows 热键、Android 悬浮球、跨 App 截图等）；PWA 不得虚假承诺这些能力。

### 1.2 不可违反的原则

- **先核对基准，再写代码**：任何 AI 不得只凭聊天摘要、旧截图或文件名判断当前实现。
- **先业务语义，后视觉**：金额、账户、分类、转账、删除恢复、权限和同步语义正确后，才做视觉收敛。
- **原型不是后端契约**：原型负责页面与交互参考；业务语义仍受 PRD / 已裁决事项约束。
- **不把技术存在等同于功能完成**：有 API 不代表 UI 已接通；有 manifest 不代表 PWA 已完成；有 Outbox 抽象不代表数据已持久化。
- **分阶段交付、逐项验收**：每阶段必须有证据、测试、截图和退出条件；不得用“基本完成”跳过。
- **不擅自扩大范围**：未裁决的冲突进入决策清单，不能由实施 AI 自行选边。

## 2. 文档权威与原型基准（开工前必须对齐）

### 2.1 权威顺序

遵守 `workbuddy/多AI对齐规范.md` 的字段和语义约束：

1. `docs/FastLedger-枚举字典.md`：字段、枚举、金额/状态等数据契约。
2. `docs/FastLedger-落地方案.md`：技术架构、API、事务、同步、安全等技术设计。
3. `docs/FastLedger-产品需求文档-PRD.md`：产品范围、业务规则、权限和验收。
4. `docs/FastLedger-开发WBS.md` 与开发指南：任务拆分和参考实现，必须跟随前三者。
5. 原型与设计规范：用于页面结构、导航、视觉和交互体验的目标参考；与上位业务契约冲突时先登记冲突并请求 Owner 裁决。

### 2.2 当前存在的基准冲突，不得忽略

仓库当前至少有两套原型/设计来源：

- `prototype/`：README 声明为 13 个核心页面的可交互原型，包含首页账单、截图识别、手动记账/转账、交易详情、账户、两级分类、投资资产、预算、报表、导出、家庭成员、设置等。
- `prototype-v2/`：`docs/FastLedger-Web设计规范.md` 的取证与示范来源，主要用于新版主题 token 和页面视觉/交互规范。
- `docs/FastLedger-交接文档-2026-11-02.md` 第 6 节曾将原版 `prototype/` 作为前端还原基准；而 Web 设计规范又以 `prototype-v2/` 为主题依据。

**执行规则（暂行）**：
- `prototype/` 作为页面清单、业务流程和交互基准。
- `docs/FastLedger-Web设计规范.md` / `docs/design-tokens.json` 作为当前主题、颜色、字体、间距、组件状态的视觉规范。
- `prototype-v2/` 仅在不与上述功能基准冲突时作为视觉补充；不得仅凭 v2 页面改动覆盖原版原型的业务流程。
- 第一阶段必须把两套原型逐页对照，形成差异表并由 Owner 确认最终基准。若 Owner 指定 v2 全面取代原版，应先更新本文和相关文档，再实施。

### 2.3 已知产品冲突，必须先裁决

| 冲突 | 现有依据 | 执行规则 |
|---|---|---|
| Web / PWA 是否提供截图识别 | PRD §5.2 对 Web OCR 有范围限制；Web 设计规范含截图识别页；PWA 指导书只建议评估用户主动选图的本地 OCR | 不擅自把 Web OCR 当作必做或已承诺。PWA 首期不承诺跨 App 截图；如需用户选图本地 OCR，先由 Owner 裁决并补 PRD |
| 删除是否永久删除 | PRD §4.4、§10.9 与 [1.10] 已确定软删除、恢复、审计；原型可能表现为删除后从列表消失 | 业务上必须保留软删除/恢复/审计；视觉上可按原型做确认和列表移除，但不能改成不可恢复硬删除 |
| 分类/账户管理 | 后端已有分类和账户相关 API；当前 Web 页面未完整接通 CRUD | 不得将其描述为“后端没有功能”；先盘点 API 契约，再补前端集成与权限/引用保护 |
| 注册入口 | CHANGELOG [1.57] 记录 Web 注册入口新增，服务端可关闭公开注册 | 不得为追求原型一致擅自删除；按 PRD 和服务端开关保留正确状态 |
| 多账本入口 | PRD 已有多账本要求 | 不得删掉多账本能力；可以按 Owner 确认的默认账本/常用账本体验优化入口 |

## 3. 已知现状与本轮独立核对结论

以下是本方案编制时对 `main` 当前代码和文档的核对摘要；实施 AI 必须在开工时重新核对文件、行号和最新提交，不得把摘要当成永久事实。

### 3.1 Web 实现与原型的主要差距

- 现有 Web 入口由 `server/web/dist/` 静态资源构成，并由 Go embed 托管；当前前端为原生 HTML / JavaScript / CSS，不应假定存在 npm 构建链。
- 当前实现有登录、账本、交易表格、账户对账、回收站、报表、导出、预算、投资资产、成员和设置等页面/入口，但这不等于原型页面流程已还原。
- 当前交易主视图以筛选、分页和批量操作的表格为主；原型目标包含首页月度概览、按日期分组的账单流、点击账单进入交易详情等体验。
- 当前未发现完整独立交易详情页面/路由；后端已有单笔交易读取 API，需核对后接入。
- 当前未发现完整分类管理前端；后端已有分类 CRUD 处理函数和路由。账户页面也需区分“只读 UI”与后端已有的账户 CRUD API。
- 当前窄屏 CSS 主要压缩导航/边距和隐藏表格列，不等于完整移动端：仍需手机底部 Tab、中央记账主入口、卡片式账单流、触控尺寸、安全区、键盘适配等。
- `docs/FastLedger-Web设计规范.md` 已给出移动导航、首页、详情、分类、报表等明确设计方向，可作为视觉与交互验收补充。

### 3.2 PWA / 离线现状

- `client/web/manifest.json` 的存在不等于 PWA 已交付。
- `server/web/dist/` 是现有 Go embed Web 客户端；PWA 专项指导书推荐在此基础上演进移动优先 PWA，Flutter 原生端并行保留。
- 当前 Flutter `LocalStore` 仍有 InMemory 实现；不得把现有抽象或客户端 Outbox 直接等同于生产级浏览器持久化。
- 完整离线必须包含 IndexedDB 业务数据层、持久 Outbox、冲突箱、同步游标、restore_epoch、Service Worker 静态缓存白名单、本地分析和加密备份/恢复；只缓存 HTML/CSS/JS 不算完整离线。

### 3.3 本轮不作出的结论

- 不沿用交接文档中未经评分矩阵证明的“50–55% 还原度”作为量化事实。应先建立逐页面、逐交互、逐断点的加权验收矩阵，再计算覆盖率。
- 不把后端 API 已存在误判为整个功能已完成，也不把前端 UI 缺失误判为后端能力缺失。
- 不把“Web 无 OCR”直接判为缺陷；按 §2.3 先解决 PRD 与原型的范围冲突。

## 4. 总体路线与阶段依赖

建议按以下顺序推进。阶段编号用于跨 AI 任务交接；PWA 专项编号继续沿用指导书的 `5P.1–5P.14`，不替换原 WBS 阶段 0–7。

| 阶段 | 名称 | 目标 | 进入条件 | 退出条件 |
|---|---|---|---|---|
| R0 | 基准冻结与差异盘点 | 统一原型、PRD、设计规范、当前代码基准 | Owner 同意启动盘点 | 页面/交互矩阵、冲突裁决清单、代码/API 盘点经确认 |
| R1 | Web 业务闭环与页面结构 | 补齐首页账单、详情、账户/分类 CRUD 接线等核心体验 | R0 通过；业务语义无未决阻塞 | 核心页面可用，真实 API 联动，业务回归通过 |
| R2 | 桌面/移动响应式还原 | 还原导航、账单卡片、表单、断点与主题 | R1 核心数据流稳定 | 手机与桌面截图/交互验收通过 |
| R3 | PWA Shell 与安装能力 | Manifest、Service Worker、离线启动壳、版本更新 | R0 技术 PoC 和安全边界通过；R2 基础 UI 可用 | Android / iOS 真机可安装、更新、离线打开静态壳 |
| R4 | IndexedDB 与在线缓存 | 结构化本地库、schema 迁移、登录后缓存、覆盖范围提示 | R3 通过；存储方案选型获批 | 重启保留缓存、迁移失败不清库、账本/用户隔离 |
| R5 | 离线记账与同步闭环 | Outbox、push/pull、冲突箱、权限变化、restore_epoch | R4 通过；离线操作白名单确定 | 离线新增/转账可重启保留、同步幂等、冲突可处置 |
| R6 | 离线分析与本地备份恢复 | 本地报表、加密备份、校验、staging 恢复 | R4 通过；备份格式/加密参数获批 | 断网分析可解释；正确恢复；损坏文件不破坏原数据；恢复不自动 push |
| R7 | 安全、跨端验收与发布 | 安全审计、浏览器矩阵、端到端与文档收口 | R1–R6 按范围完成 | 真机验收、回归、部署/用户文档、CHANGELOG 完成 |

依赖关系：
- R0 → R1 → R2。
- R0 → R3 → R4 → R5。
- R4 → R6。
- R2、R5、R6 → R7。
- R1/R2 可先推进桌面 Web 的原型还原；R3/R4 可在 R2 期间做隔离 PoC，但不得在业务基准未冻结前铺开大规模 PWA 开发。

## 5. 各阶段实施任务与验收

### R0：基准冻结与差异盘点（最高优先级，禁止跳过）

**目标**：回答“要还原哪套原型、每个页面应如何工作、现有实现到底差在哪里”。

交付物：
1. 页面目录：逐一登记 `prototype/` 的 13 个核心页面、入口、路由、弹层、空/加载/错误/成功状态。
2. 原型交互清单：每个可点击元素的行为、输入校验、成功/失败反馈、数据联动、返回路径。
3. 原型双版本对照：`prototype/` 与 `prototype-v2/` 的页面/流程/视觉差异，标明是否影响业务语义。
4. 当前 Web 代码映射：每个原型页面映射到 `server/web/dist/index.html`、`app.js`、`style.css` 中的路由、render 函数、API 调用；缺失项明确标“前端未实现 / API 未接通 / 后端无能力 / 产品待裁决”。
5. 后端 API 能力矩阵：账户、分类、交易详情、删除恢复、报表、预算、资产、成员、设置等逐项列出方法、路径、鉴权、权限、请求/响应和测试。
6. 基准冲突清单：至少覆盖 §2.3 的 OCR、删除、注册、多账本，以及原型版本优先级。
7. 验收基线：同一视口截图、页面状态截图、真实数据样例和可重复操作脚本。

**验收**：
- 13 页逐页有“原型证据、当前实现证据、差异、目标、影响、依赖、测试”。
- 交互元素不得只写“可点击”；必须说明点击前置条件和点击后的可观察结果。
- 未确认的业务决策必须有 Owner 决议或明确标记“阻塞，不开发”。
- R0 未通过，不允许以“按理解先做起来”进入大规模页面改造。

### R1：Web 业务闭环与页面结构

建议顺序：
1. 首页：月度收入/支出/结余概览；按日期分组账单流；日期小计；账本/月度筛选；记一笔入口。
2. 交易详情：从首页/列表点击进入；展示完整字段；编辑能力严格按服务端真实路由和 PRD；删除二次确认；删除后遵循软删除、回收站和审计。
3. 记一笔：支出/收入/转账类型切换；转账双账户字段；表单校验；pending 防双击；成功 toast；返回首页并刷新概览与账单流。
4. 账户：读取、创建、编辑、归档/删除（仅当 API 和引用保护规则支持）；余额/类型/净资产展示。
5. 分类：两级分类展示、创建、编辑、停用/删除；核对交易引用、默认分类和服务端校验。
6. 其余页面：预算、报表、导出、投资资产、成员、设置按原型逐项核对，不因已有同名菜单就判定完成。

**特别约束**：
- 先核对交易 Update 是否已开放。若服务端当前只允许 GET/POST/DELETE/restore/recycle，前端不得自行伪造 PUT；需要编辑时先走产品/架构裁决并更新 API、审计和测试守卫。
- 转账必须保持唯一创建入口、双边原子、同版本、幂等；不得由前端拆成两笔普通交易。
- 删除交易/转账不得硬删除；转账必须整笔删除/恢复。
- 账户/分类删除必须尊重服务端引用保护；禁止前端绕过服务端错误。

**退出条件**：
- 每个核心动作有真实 API 请求与响应证据；不允许仅靠 mock/localStorage 演示通过。
- 首页、详情、记账、账户、分类的新增/变更/删除后数据联动正确。
- Go 服务端测试、Web 静态资源检查和关键 API 集成测试通过。

### R2：桌面与手机响应式还原

**目标**：桌面 Web 与手机 Web 是同一业务能力的不同布局，不是桌面表格压缩版。

必须实现/验收：
- 手机底部 4 Tab：首页 / 记一笔（中央主按钮）/ 报表 / 我的；桌面采用设计规范定义的顶部导航。
- 手机首页使用日期分组账单卡片；不得通过隐藏关键列让用户失去账户、分类、备注等必要信息。
- 表单适配数字键盘、软键盘遮挡、滚动定位、safe-area、横竖屏和窄屏。
- 触控目标原则上不小于 44×44 CSS px；弹窗/抽屉适配手机高度和返回操作。
- 视觉使用 `docs/FastLedger-Web设计规范.md` 和 `docs/design-tokens.json`；禁止业务 CSS 散落硬编码主题色。
- 处理加载、空数据、网络错误、权限不足、离线、同步中、冲突等状态。
- 桌面既有表格/筛选/批量操作不得因移动改造回归。

**截图验收矩阵**：至少覆盖 360×800、390×844、430×932 手机视口，以及 1280×800 桌面视口；同一页面同一数据、同一状态进行原型与实现对照。具体设备可按项目测试环境调整，但必须记录实际 viewport 和浏览器。

### R3：PWA Shell 与安装能力（对应 PWA 指导书 5P.1–5P.4）

- 先做 Android Chrome / iOS Safari 技术 PoC，验证安装入口、Service Worker 生命周期、离线导航、更新策略和安全上下文。
- 沿用现有 Go embed 托管，除非 PoC 证明必须改变；Flutter Web 不得未经比较测试就替代。
- Manifest、图标、启动页、主题色、display、scope 与 start_url 完整。
- Service Worker 只缓存版本化静态 App Shell 和必要静态资源；`/api/*`、`/ws`、用户私有响应、Token、备份文件和错误响应全部 network-only / 不缓存。
- 版本更新时提示用户并安全激活；避免旧 HTML 引用已删除的资源。
- 离线启动显示明确离线状态；没有本地业务库时不得伪装成完整离线可用。

**退出条件**：Android Chrome 和 iOS Safari 真机安装、关闭网络后重新启动、静态壳加载、更新切换均有录屏/日志证据。

### R4：IndexedDB 与在线缓存（对应 5P.5–5P.6）

- IndexedDB 是 PWA 业务数据权威本地持久层；页面不得直接散落数据库访问，统一 repository。
- schema 版本化迁移；迁移失败停止写入、保留旧数据并提示处理，禁止清空后重建。
- 业务记录、账户、分类、账本、同步水位、restore_epoch、Outbox、冲突箱分开建模。
- 金额始终整数分；禁止 JS Number 浮点累加；明确 BigInt / JSON 的边界。
- 登录后只缓存当前用户有权访问的账本；换用户、退出、成员移除和权限收紧执行清理。
- 展示最后同步时间、缓存账本、记录数量和覆盖范围；明确“本机已缓存数据，不代表服务端全量”。

**退出条件**：杀进程/重启浏览器后缓存仍在；升级 schema 不丢数据；不同用户/账本数据不串；配额不足有可恢复错误提示。

### R5：离线记账与同步闭环（对应 5P.7–5P.8）

- 本地业务写入和 Outbox 入队必须在同一 IndexedDB transaction；生成一次稳定 `clientUuid`。
- 联网按既有顺序 push → pull；成功回执更新本地状态并出队。
- 网络错误/5xx 退避重试；相同 clientUuid 重放完全相同请求体；修改内容必须创建新操作键。
- 409、`ENTITY_DELETED`、403、字段校验错误进入可见冲突/失败箱，不得静默丢弃。
- WebSocket 仅作变更提示，断线重连依然执行 Pull。
- 账本版本以服务端 `book_versions` 为准，不以客户端时间戳替代。
- 可见性变化、成员移除和角色变更按已定事件契约清理本地权限范围；`restore_epoch` 变化时暂停 Push、隔离旧队列、全量重建并逐项处置。
- 离线允许操作白名单必须逐项列出；编辑/删除/账户分类管理不能因为“离线新增可用”就默认可排队。

**退出条件**：
- 离线新增普通交易与转账，断网期间强制关闭/重启浏览器后仍存在。
- 恢复网络后重复触发同步不产生重复账目；服务端幂等回执正确。
- 409 / ENTITY_DELETED / 403 / 校验失败均可见、可处置且不丢队列。
- 权限变化和 restore_epoch 演练证明旧数据不会泄露或回流。

### R6：离线分析与本地备份恢复（对应 5P.9–5P.11）

离线分析：
- 首期至少覆盖本月收支/结余、日/月趋势、分类占比、账户汇总、关键词和时间筛选。
- 分析只基于 IndexedDB；明确缓存范围、记录数、最后同步时间；不可把 API 断网空响应当成零。
- 金额聚合使用整数分。

本地备份/恢复：
- 采用版本化归档和 manifest，包含格式/schema 版本、导出时间、账本范围、记录数量、校验信息和同步水位。
- 默认加密；WebCrypto 算法、KDF 参数、随机 salt/IV 和文件格式须先经安全审查与 Owner 确认。
- 不包含 Token、PAT 明文、服务端密钥、无权数据或 Service Worker 缓存。
- 导入先 staging，完整校验后切换；错误口令、损坏文件、版本不兼容不得覆盖当前数据。
- 恢复默认仅恢复到本机，绝不自动 Push；与服务端合并必须作为另一个显式、高级、重新鉴权的流程。

**退出条件**：离线分析标识数据范围；正确口令恢复成功；错误口令/篡改/截断/不兼容文件均失败且原数据不变；恢复后无自动网络写入。

### R7：安全、跨端验收与发布（对应 5P.12–5P.14）

- 审查 SW 缓存规则、XSS、CSP、安全响应头、Token 生命周期、退出清理、设备共用与本地数据隔离。
- Android Chrome、iOS Safari（主屏幕安装）、桌面 Chrome 完成安装、更新、断网、存储配额、导入导出和恢复演练。
- 端到端覆盖：在线记账 → 断网记账 → 重启 → 联网同步 → 多端一致；删除/权限变化/恢复世代异常；本地备份恢复。
- 对关键业务执行 Go 单测/集成测试、Web API 测试、浏览器自动化与真机手工测试。
- 更新 PRD、落地方案、WBS、README、部署文档、CHANGELOG；只记录实际完成和真实测试结果。

## 6. 每个 AI 任务的强制交付格式

每次只领取一个阶段内可独立验收的小批次。不得同时跨越多个阶段进行大规模重构。

### 6.1 开工前回执

必须提交：
1. 当前 `main` commit SHA 和工作分支。
2. 本次阅读的规范/决策文档及其版本。
3. 任务编号、范围、明确不做的内容。
4. 相关原型页面/交互截图及路径。
5. 当前实现的文件、函数、路由和行号。
6. 真实 API 能力、权限和请求响应契约。
7. 影响的测试、文档和回归范围。
8. 未决产品/技术问题；若有阻塞项先停，不得自行裁决。

### 6.2 实施计划

每项子任务至少包含：

| 字段 | 要求 |
|---|---|
| 任务 ID | 沿用本方案阶段号 / WBS 编号；新缺陷按多 AI 规范编号 |
| 目标 | 一句话可观察结果 |
| 原型证据 | 文件/页面/交互/截图 |
| 当前证据 | 文件路径、函数/路由、行号、必要代码片段 |
| 差异 | 当前行为与目标行为的明确对比 |
| 根因 | 代码缺失、API 未接线、数据契约、权限、样式、路由或产品冲突 |
| 修改范围 | 精确文件清单和拟修改函数 |
| 依赖 | API/文档/决策/其他任务 |
| 验收 | Given / When / Then，可操作、可判定 |
| 测试 | 命令、浏览器/设备、预期结果 |
| 风险 | 数据迁移、兼容、隐私、安全、回归 |

### 6.3 完工回执

必须提交：
- 实际改动文件清单与关键 diff 摘要。
- 每条验收用例的预期、实际、证据（截图/录屏/日志/测试输出）。
- 执行的完整测试命令和真实结果；未执行必须明确写“未执行”，不得写通过。
- 原型与实现同 viewport 对照图；交互任务提供操作录屏或可重复步骤。
- 未完成项、已知风险、下一任务建议。
- PRD / 落地方案 / WBS / README / CHANGELOG 是否同步，具体章节和版本。
- 说明是否改变 API、数据库 schema、权限、同步契约或客户端持久化格式。

## 7. 质量门禁与禁止事项

以下任一情况发生，阶段不得标记完成：

1. 只有页面截图，没有真实 API 数据联动证据。
2. 只有 API 测试，没有页面交互和错误状态验收。
3. 只在桌面浏览器缩窄窗口测试，未在手机真机测试。
4. 只测在线流程，未测离线重启、重复同步和冲突处置。
5. 只测试正确备份文件，未测错误口令、损坏文件和不兼容版本。
6. 以 Service Worker 缓存代替 IndexedDB 业务持久层。
7. 将本地备份恢复后自动全量 Push。
8. 绕过服务端权限、软删除、审计、幂等、版本或 restore_epoch。
9. 把原型演示数据、mock、localStorage 结果当作后端集成完成。
10. 未更新 CHANGELOG / README 导航，或将未实测能力写成已交付。
11. 未经 Owner 裁决擅自解决 PRD/原型冲突。
12. 大批量改动未分阶段提交，导致无法定位回归来源。

## 8. 验收矩阵建议

| 维度 | 核心问题 | 证据 |
|---|---|---|
| 页面覆盖 | 原型 13 页和入口是否逐项覆盖 | 页面矩阵、路由清单 |

| 响应式 | 手机/平板/桌面是否适配 | 设备矩阵截图 |
| PWA 安装 | 安装、启动、更新、离线壳是否可用 | Android/iOS 真机记录 |
