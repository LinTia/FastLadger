《原型还原与 PWA 分阶段实施总方案》§5 将 R0 定义为**基准冻结与差异盘点阶段**，交付物是页面/交互清单、双原型差异、代码/API 映射、基准冲突清单、验收基线与可重复证据。

1. **R0 通过不等于把所有 R0-E 功能全部开发完。** 期初余额、支付渠道、账本可见性、商户字段等，需在 R0 中完成准确取证、需求追溯、技术契约和后续实施拆分；业务实现按经批准的后续阶段执行。

3. 不得为“让 R0 通过”而擅自启动 R1、修改 PRD/WBS 核心范围、改变既定业务语义，或把未验证写成已验证。
4. 明确列为 R0 门禁的证据缺口（尤其截图基线和 R0-E-35）不能静默挪到 R1；如需例外，必须由 Owner 明确签署风险接受及范围变更。

## 3. 技术裁决文件的最小补齐

### 3.1 D-4：期初余额时间语义（实现前必须补）

现有模型采用 opening_balance（整数分）+ opening_balance_at（Unix 秒，可空）+ balance 物化值，方向可保留。文档尚未完整定义“用户输入的本地日期/时间如何变成 Unix 秒”。

实现任务单必须明确：

- 输入是日期还是日期时间；若 UI 只输入日期，基线统一解释为该本地日期的 00:00:00。
- 客户端时区来源、timezoneOffset 的单位与正负号，必须对照现有交易 DTO/客户端转换实现，不得自行猜测。
- 服务端接收的是已经转换好的 Unix 秒，还是接收本地时间 + offset；两端只允许一种权威转换路径，避免重复转换。
- 交易 txTime 与基线比较必须使用同一时间单位（Unix 秒）和同一时区解释。
- 测试：跨日、跨时区、UTC+/-偏移、夏令时切换地区、基线前一秒/相等/后一秒；历史交易改期跨越基线；转账两账户取较晚基线；删除/恢复与并发。
- 若沿用固定 offset 而非 IANA 时区，必须明确这是 MVP 限制：固定 offset 无法表达历史夏令时规则，不能宣称支持任意历史时区换算。

**状态**：这是 D-4 实施前的技术契约补充，不代表要求在 R0 阶段开发期初余额功能。离线账户创建命令、clientUuid 幂等、冲突/重放/权限/恢复语义仍是后续实现的前置任务。
