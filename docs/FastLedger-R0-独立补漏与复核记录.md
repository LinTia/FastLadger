## 4. 补充差异清单（新增 R0-E-20 起）

> 这些是 R0 盘点差异，不是代码已修复任务。严重度按《多 AI 对齐规范》统一口径预标；需后续实施任务按完整 finding 字段拆解。未运行端到端用例的项目明确标“静态代码已证实，运行时待测”。

### R0-E-20：首页第三张卡金额口径错误

- **严重度：P1（会计正确性）**
- **位置**：`server/web/dist/app.js` L1950–1965，`renderHome()`。
- **证据**：代码执行 `let balance = 0; for (const a of accs) balance += a.balance || 0;`，随后显示 `mkCard("结余", ..., "净资产")`。
- **问题**：同一数值同时被标为“结余”和“净资产”。它既不是本月收入减本月支出，也不是净资产公式。负债账户余额按枚举字典规定“正数=欠款”，直接相加会把负债加到资产侧；持仓市值也未纳入。
- **预期**：本月结余 = 本月收入 − 本月支出；净资产 = Σ资产账户余额 + 持仓市值 − Σ负债账户余额。首页卡片应明确只显示哪一个口径，不能混用。
- **建议**：按设计规范首页三卡显示“本月支出 / 本月收入 / 本月结余”；净资产放资产总览，并使用后端 `/net-worth` 口径。不要在前端重新发明净资产算法。
- **验收**：构造资产 1,000 元、信用卡欠款 300 元、持仓 200 元、本月收入 500 元/支出 200 元；首页结余应 300 元，净资产应 900 元。分别断言，确保不会显示 1,300 或 700 等混合口径。

### R0-E-21：首页账单行缺少账户/渠道，首页筛选缺失

- **严重度：P2**
- **位置**：`app.js` L1872–1927；PRD §4.2。
- **证据**：账单行只拼接分类、备注/商户、时间、金额；没有 `accountName(tx.accountId)`（转账行除外），没有 payment channel 展示。首页函数也没有筛选控件；筛选存在于独立交易总表。
- **问题**：PRD 要求每条账单显示账户与渠道，并支持时间、账户、分类、类型、关键词筛选。独立交易总表筛选不能自动等同于首页筛选。
- **建议**：账单行按可读性显示账户和渠道标签；首页提供符合移动端布局的筛选入口，并复用统一查询参数/筛选状态。
- **验收**：同一张信用卡分别经微信、支付宝支付时，账单能区分渠道且显示相同资金账户；时间/账户/分类/类型/关键词筛选均能改变首页列表与空态。

### R0-E-22：交易详情字段展示不完整

- **严重度：P2**
- **位置**：`app.js` L2000–2015；PRD §4.3.3、§4.4；设计规范 §8.2。
- **证据**：详情展示账户、分类、日期、备注；未展示 paymentChannel。备注表达式为 `tx.note || (tx.merchant ? "商户：" + tx.merchant : "—")`，备注非空时商户不显示。
- **问题**：用户无法从详情核对支付渠道；备注与商户同时存在时丢失一个字段。
- **建议**：商户、备注、支付渠道分别展示；转账详情展示转出/转入账户及双方必要信息。
- **验收**：构造 merchant 与 note 同时非空、paymentChannel=微信的交易，详情三者均可见；无值字段显示统一占位。

### R0-E-23：手动记账/编辑表单缺少支付渠道选择器

- **严重度：P1（核心账务维度缺失）**
- **位置**：`index.html` L40–75；`app.js` L529–640；PRD §4.3.1、§4.3.3；交易更新语义设计 §1。
- **证据**：新建表单只有类型、金额、账户、对方账户、分类、日期、备注；没有 paymentChannel、merchant 控件。新建请求体也没有显式 paymentChannel/merchant。编辑表单没有渠道选择，虽在 PUT body 中沿用 `tx.paymentChannel || 0`，但用户无法修改。
- **问题**：支付渠道是与资金账户分离的核心维度，缺失会让微信/支付宝渠道无法正确标注。编辑契约要求 paymentChannel 字段全量替换语义，当前 UI 不能编辑它。商户字段的端到端缺失另列 R0-E-37。
- **建议**：补充渠道选择和商户输入；编辑表单预填并允许编辑渠道，商户是否允许修改必须遵守交易更新语义设计中的不可变字段（该文档将 merchant 列为不可变），因此 merchant 可能只能创建时录入、详情只读，不能擅自开放 PUT 修改。
- **验收**：新建表单可选择并提交 paymentChannel；详情能展示；编辑表单预填当前渠道并按已裁决契约修改；类型切换与转账时字段显隐符合规范。

### R0-E-24：删除确认文案与软删除/恢复能力矛盾

- **严重度：P2**
- **位置**：`app.js` L2007–2015；PRD §4.4；路由 `router.go` 交易 restore 路由。
- **证据**：确认框文案为“删除后将无法恢复”；系统提供软删除、回收站和 `POST /transactions/:txId/restore`。
- **问题**：错误告知用户删除不可恢复，和真实产品能力不一致。
- **建议**：文案改为“交易将移入回收站，可在保留期内恢复”，具体保留期按已裁决策略；转账须强调整笔删除/恢复。
- **验收**：删除后可在回收站找到并恢复；恢复后余额、报表和列表回滚正确；确认文案与实际保留策略一致。

### R0-E-25（并入 R0-E-15，不单独计数）：Web 前端没有 WS 或 sync pull/push 客户端

> 本项是对原 R0-E-15 的证据补强，不是第二个独立缺陷；主编号保留为 R0-E-15。

- **严重度：P2**
- **位置**：`index.html` L1–75；`app.js` 全文；`router.go` L125–135、L215–235。
- **证据**：后端注册 `GET /api/v1/ws`、`GET /books/:id/sync/pull`、`POST /books/:id/sync/push`；当前 HTML 只加载 `/app.js`，该 JS 未实现 WebSocket，也没有 sync pull/push API 调用。
- **问题**：后端路由存在不等于浏览器客户端接通。Web 当前以 REST 读写页面数据，不能据此宣称跨设备实时刷新或增量同步已在 Web 端实现。
- **建议**：按 R 阶段规划明确 Web 端同步范围；若本阶段仅 REST 在线使用，应如实标注“无实时客户端同步”，不要误写“仅 WS”。
- **验收**：双浏览器/双账号场景中，新增、更新、删除及权限变更的事件/重拉行为可复现；断线重连后补齐数据；无权成员不会收到明细；否则明确将 Web 同步列为未实现。

### R0-E-26：邀请码撤销后端有路由，Web 无撤销流程

- **严重度：P2**
- **位置**：`app.js` L1636–1685 及成员列表后续代码；`router.go` 邀请撤销路由；`book_handler.go` revokeInvite。
- **证据**：前端仅调用 `POST /members/invite` 生成邀请码并展示 `data.code`；后端另有 `POST /members/invite/:inviteId/revoke`，但当前前端没有撤销调用、邀请 ID 列表/管理入口。
- **问题**：已生成但未使用的邀请码无法从 Web UI 撤销。当前 create handler 返回 code/role/expiresAt，不返回 inviteId；应核对是否存在可供前端列举邀请的接口，不能凭空接撤销 API。
- **建议**：先确认服务端是否提供邀请列表/详情能力；若无，设计安全的最小列表/撤销 API，再实现 UI。不要仅凭邀请码字符串推导数据库 ID。
- **验收**：管理员能看到尚未使用邀请、撤销指定邀请；撤销后兑换失败；普通成员不能撤销；审计日志有对应记录。

### R0-E-27（并入 R0-E-19，不单独计数）：账本可见性没有可操作开关，当前徽标读取的字段粒度不正确

> 本项补充 R0-E-19 的字段粒度与隐私提示证据，不另行统计；主编号保留为 R0-E-19。

- **严重度：P1（隐私控制缺失/状态误导）**
- **位置**：`app.js` L1636–1775；`router.go` `PUT /books/:id/visibility`；PRD §7.3；枚举字典 §11。
- **证据**：前端表格按每个成员的 `mb.canViewOthers` 显示“已开启/关闭账本可见”，但 MVP 权威字段是账本级 `books.members_can_view_others`；`book_members.can_view_others` 是预留的成员级覆盖。当前页面没有调用 `PUT /books/:id/visibility`，也没有常驻隐私提示。
- **问题**：用户无法在 Web 页面切换 MVP 账本级互看设置；同时逐成员徽标可能把预留字段误显示成有效设置状态。
