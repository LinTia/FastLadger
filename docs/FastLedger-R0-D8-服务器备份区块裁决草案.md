## 2. 需求依据（为什么设置页要有这两个区块）

| 来源 | 条款 | 要求 |
|---|---|---|
| PRD §4.12 | 我的 / 设置 | 个人资料、账号安全、密码修改；长期 API Token 管理；**服务器信息、数据备份与恢复入口**；（管理员）系统级设置、外部 LLM 配置、备份策略 |
| Web 设计规范 §8.1 | 导航结构 | 设置（资料、API Token、**服务器信息、备份**） |
| Web 设计规范 §8.2 | 关键页面交互规格 | 设置：API Token 管理（生成/复制/撤销）、**备份入口**、退出登录 |
| 部署交接 §7 | 备份与恢复 | 备份 = 备份 `data/` 目录（排除 `instance.meta`）；每日 cron `sqlite3 .backup`；恢复 = 停服→换库→`instance bump`→启动 |

**结论**：四份文档在"设置页应包含服务器信息 + 备份入口"这一点上**一致**，需求入口已确定。

## 3. 跨文档冲突核查结论

逐项比对 PRD §4.12 / 设计规范 §8.1–8.2 / 部署交接 §7 / 落地方案 §8.3：

- **需求层一致性**：四者均要求设置页暴露服务器信息与备份能力，无矛盾。
- **实现层缺口（非文档冲突）**：当前 Web 端**没有**任何可供设置页安全读取的服务器信息 / 备份状态 API（见 §5）；备份由服务器 cron 脚本直接执行，**不写任何元数据**。这是"需求已定但安全实现契约未定"的缺口，正是 D-8 要裁决的对象，不是文档之间互相打架。
- **权限语义一致**：PRD §12 明确"实例管理员"（`is_instance_admin`）与"账本 owner/admin"**正交**；设计规范 §8 的"设置"入口不隐含任何账本角色自动获得实例级权限。本草案§7 的权限模型与此一致。
- **`restoreEpoch` 语义警示**：PRD §12 / 落地方案 §8.3 / meta.go 均明确 `restore_epoch` 是"**实例被从备份恢复的次数**"计数器，**不随备份回滚**；它**不是**"上次备份成功"的时间戳或成功标志。任何"把 `restoreEpoch` 当成备份成功状态"的解读都是错误，本草案禁止。

> **未发现 PRD / 落地方案 / 设计规范 / 部署交接之间的实质冲突。** 若有后续实现中暴露的新矛盾，单独上抛 Owner，不自行改写文档。

## 4. `/healthz` 实测与安全边界（源码实读 + 历史运行实测）

**代码位置**：`server/internal/api/router.go:109–120`。

**真实返回结构**（源码逐字）：

```json
{ "code": 0, "msg": "ok",
  "data": {
    "status": "up",
    "schemaVersion": <int>,
    "instanceId": "<随机固定值，仅当 instance.meta 存在>",
    "restoreEpoch": <int，仅当 instance.meta 存在>
  }}
```

**鉴权状态**：`/healthz` 在 `NoRoute` 之前显式注册（`router.go:109`），**无任何鉴权中间件**，所有请求（含未登录、含 CDP/外部探测）均可访问。它**不计入 UI 控件验收分母**（主报告 §5.3 备注）。

**安全边界（已暴露字段均为非敏感）**：

- 暴露：`status`（进程存活）、`schemaVersion`（迁移版本号）、`instanceId`（实例随机标识）、`restoreEpoch`（恢复世代计数）。
- **绝不暴露**：服务器文件路径、数据库文件内容、`EBK_*` 环境变量、`cron` 日志、密钥、备份目录、任何私账数据。

**历史运行实测**：[1.65] 记录本地启动后端后 `GET /healthz` 实测 `data.status == "up"`、schema 为 v8；本轮**未重新 curl**（沙箱/端口约束），字段契约以源码 `router.go:109–120` 为权威，与历史实测一致。

> **`restoreEpoch` 误读警示（Owner 特别强调）**：它不是备份成功标志。它只在运维执行 `fastledger instance bump`（恢复数据文件之后）时 `+1`，用于让客户端察觉"服务端整体回退过"并触发全量重建。设置页**不得**用它推断"备份是否成功"。

## 6. 未来需要的后端 API、数据字段、权限模型、备份元数据来源

### 6.1 建议 API 契约（草案，未实现）

```
GET /api/v1/system/info           # 鉴权；只读非敏感
  → { serviceUp, serviceVersion, schemaVersion, instanceId, dataSizeBytes }

GET /api/v1/system/backup/status  # 仅 isInstanceAdmin；数据源见 6.4
  → { lastSuccessAt, backupCount, lastSizeBytes, source }
  → 未接入时返回 { available:false }，前端显示"暂未提供状态查询"
```

### 6.2 数据字段

- **新增（建议）**：`dataSizeBytes`（运行时计算 DB 文件大小 / 关键表行数汇总）；`serviceVersion`（构建期注入）。
- **已有可复用**：`schemaVersion`（迁移版本）、`instanceId` / `restoreEpoch`（`instance.meta`，但 `restoreEpoch` 仅作世代标识，**不作备份成功标志**）。
- **不在 Web 范围**：私账明细、文件路径、环境变量、密钥、cron 日志、备份目录列表。

### 6.3 实例管理员权限模型（与 PRD §12 对齐）

- **账本 Owner/Admin**：仅限本账本内管理（成员、分类、账户、设置、可见性）；**不等于**实例管理员；不自动获得实例级权限。
- **实例管理员**（`is_instance_admin == true`）：可整库下载、改全局配置、查看实例级日志、启停备份任务；**不可默认读取任意私账明细**。
- **守卫**：任何实例级路由（含未来备份状态 API）须 `requireInstanceAdmin` 中间件，不得仅凭账本角色放行。

### 6.4 备份任务元数据来源（关键缺口）

当前 cron 备份**不记录任何元数据**，因此 `backup/status` 无数据可读。建议（任选其一，均属服务端运维改进，**非 Web 代码**）：

1. **备份脚本写 manifest 文件**（如 `/var/backups/manifest.json`，含 `last_success_at` / `size` / `count`），服务只读解析；
2. **新增 `backup_runs` 表**，备份脚本写库；
3. **服务直接扫描备份目录** `mtime` / `size` 推导最近备份与份数（最小侵入，但依赖目录约定）。

无论哪种，均须**服务端先落地**，`backup/status` 才有真相来源。**未接入前，前端必须显示"暂未提供状态查询"，不得推测备份成功。**

## 7. 设置页交互草案（展示范围 / 无数据态 / 错误态 / 权限不足态）

设置页新增两个卡片：

### 7.1 服务器信息（所有已登录用户可见，只读）

| 字段 | 来源 | 说明 |
|---|---|---|
| 服务状态 | 进程存活推导 | "运行中" / "异常" |
| 服务版本 | §6.2 新增字段 | 构建版本号 |
| 数据库结构版本 | `schemaVersion` | 迁移版本 |
| 实例标识 | `instanceId` | 用于识别同一实例、排查同步世代 |

### 7.2 数据备份（**仅实例管理员可见**）

- **正常态**：最近备份时间、备份份数、最近备份大小。
- **无数据态（未接入）**：显示"暂未提供状态查询（请联系服务器管理员）"——**不推测成功**。
- **错误态（API 失败）**：红色错误提示，明确"状态获取失败"，**不回退到"备份成功"的假象**。
- **权限不足态（非实例管理员）**：区块隐藏，或显示"仅服务器管理员可见"。
- **首期不放按钮**：一键备份、一键恢复、删除备份、修改备份目录、整库下载——继续由运维流程 / CLI 完成。

## 8. 首期不开放 Web 恢复操作的理由（Owner 特别强调）

1. **破坏性 + 需文件系统写权限与进程重启**：恢复 = 停服→替换 DB→`instance bump`→启动，无法安全封装进一次 Web 请求；若让应用自身写数据目录并自重启，会放大"被攻破的 Web 会话"的破坏半径。
2. **绕过演练与审计**：当前恢复是固化运维步骤（部署交接 §7 / 落地方案 §8.3），依赖人工核对与"恢复演练必做"（PRD §10.9）。Web 一键化会跳过演练与审计留痕。
3. **不可逆、影响全局**：整库恢复影响所有账本与所有用户，误操作 RPO = 上次备份，即便有备份也丢增量；应保留在高权限、低频率的运维通道。
4. **PRD 定位为运维任务**：PRD §12 将"备份恢复"定义为运维（恢复演练必做），并非"Web 用户自助按钮"。
5. **触碰安全边界**：Web 不得直接读取服务器文件、数据库文件、环境变量、cron 日志、密钥或备份目录；恢复按钮必然触碰这些边界。

## 9. D-8 裁决结论（采纳 Owner 六原则）

Owner 于 2026-11-04 通过交互询问给出以下六项倾向，本草案**全额采纳**为 D-8 正式裁决：

1. 设置页保留「服务器信息」和「数据备份」两个区块，满足 PRD §4.12 与 Web 设计规范 §8.1–8.2。
2. 服务器信息**首期只读**，普通用户仅查看服务可用性、服务版本、数据库结构版本等非敏感信息。
3. 备份状态**仅服务器管理员（实例管理员）可见**，必须来自**服务器端备份任务的真实执行记录**；未接入时显示"暂未提供状态查询"，**不得推测备份成功**。
4. **账本 Owner/Admin 不自动等同服务器管理员**，必须区分账本级权限与实例级管理权限（与 PRD §12 正交模型一致）。
5. 首期**不开放** Web 一键恢复、删除备份、修改备份目录等高风险操作，继续由服务器管理员通过运维流程完成。
6. **不允许 Web 直接读取**服务器文件、数据库文件、环境变量、cron 日志、密钥或备份目录。

**裁决状态**：D-8 由"展示/操作边界待确认"变更为 **已裁决（采纳 Owner 六原则）**。实现（前端区块 + 后端只读 API + 实例管理员守卫 + 备份元数据来源）属 R 阶段，不在 R0，按本草案契约排期。
