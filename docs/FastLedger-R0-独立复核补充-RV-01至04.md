## R0-RV-01：首页请求失败时骨架屏残留的结论尚未证实

**发现位置**

- R0 主报告 §3「首页账单」状态列及其后「状态覆盖缺口（R0-E-12）修正」段落。
- R0 主报告 §7.5 截图执行结果及相关失败态说明。

**证据与问题**

主报告前文仍将「请求失败时 skeleton 未替换为错误态」作为已确认问题；但 §7.5 对本轮截图的说明只观察到页面主体空白和 `Failed to fetch` toast，没有看到足以确认骨架屏残留的画面，并承认失败可能发生在 `loadBookMeta` 或 `renderBillStream`，尚未用运行时日志定位具体请求。

因此，现有证据不足以把「交易列表请求失败导致骨架屏残留」作为已证实缺陷。不能把一次泛化的网络失败截图当成对指定请求失败分支的隔离验证。

**修改要求**

1. 将 R0-E-35 的结论统一标为「待运行时复验 / 阻塞」，不得在摘要、矩阵、结论中继续表述为已证实缺陷。
2. 明确区分「骨架屏已实现」与「特定请求失败时是否正确清理骨架屏」两个判断。
3. 不得仅通过修改文字关闭该项；需要真实浏览器隔离复验。

**验收标准**

- 拦截且仅拦截 `GET /books/:id/transactions`，放行登录态、账本元数据、账户和分类等依赖请求。
- 分别记录该请求 pending 与 rejected 两种状态下的页面表现。
- 保存浏览器截图、Network 请求记录、Console 日志，并注明浏览器版本、视口、复现步骤。
- 验证失败后是否清理 skeleton、是否显示可理解且可恢复的错误态、重试是否有效。
- 在证据齐备前，状态保持「待运行时复验」，不计作已关闭。

## R0-RV-02：文档基准、业务代码基准与截图基准未清晰分离

**发现位置**

- R0 主报告 §0「开工前回执」中的「当前基线 SHA」。
- R0 主报告 §3.1 的「取证基线」。
- §7.5 截图证据说明与报告顶部的基准声明。

**证据与问题**

本轮复核涉及至少两个不同用途的提交：

- `575eae3cef33dd2aada9c943e4e7ac8ccc93cf4a`：最新文档 HEAD，包含本轮 R0 文档、CHANGELOG、README 和截图资产。
- `bff6a2b351bf5a039cdf7c762ec2693fb330cd00`：二次整改时使用的业务代码证据基准；`575eae3` 相对该提交没有业务代码变更。
- 主报告 §0 仍保留更早的 `1cd56ab7830d2d3f33faf7fc5372d3824c088ae0`，容易让读者误以为当前逐控件/API 证据仍基于该旧代码快照。

问题不是要求把所有 SHA 强行改成同一个，而是没有明确区分不同证据资产的基准。

**修改要求**

在主报告开头增加统一的「证据版本基准」表，至少列明：

1. 文档版本 HEAD：`575eae3...`。
2. 业务代码证据基准：`bff6a2b...`。
3. 截图采集所对应的代码版本、截图提交/资产版本；若无法从现有记录证明截图时实际运行的代码 SHA，明确写「未独立验证」，不得推定等于代码基准。
4. 历史 `1cd56ab...` 的用途；若已不再作为本轮有效代码基准，应标注为历史快照，不要继续称为当前基线。

**验收标准**

报告首页、§3.1、§5.3、§7.5 的基准口径一致；每一类证据都能追溯到对应 SHA，且不会把文档提交误写成业务代码更新。

## R0-RV-03：逐控件清单中的「—」存在语义歧义

**发现位置**

- R0 主报告 §3.1.1 等逐控件交互表。
- 例如 `I-LOGIN-05`（登录提交按钮）、`I-BOOKS-01`（账本行链接）、`I-ACCT-01`（新增账户按钮）等条目中的空字段。

**证据与问题**

§3.1 字段口径说明已强调运行时未验证不能用「—」掩盖，但实际表格仍有多个字段使用「—」。读者无法判断它究竟表示：

- 该字段确实不适用；
- 该行为由另一条交互 ID 统一覆盖；
- 当前没有证据、尚未验证；
- 编制者遗漏了该字段。

即使某些失败反馈或数据联动已在其他交互条目说明，也需要建立可追溯引用，不能要求读者猜测。

**修改要求**

统一替换为明确语义：

- `N/A（不适用）`：该字段对该控件确实不适用，并确保理由清楚。
- `见 I-LOGIN-13`：由其他交互条目覆盖，必须引用真实存在的 ID。
- `未验证`：尚无运行时证据。
- `未实现`：代码中没有对应能力。
- `待确认`：需求或产品行为尚未裁决。

不得把空白或「—」作为以上状态的通用替代。

**验收标准**

抽查登录、账本、账户、交易表单等至少 10 条记录；每个原先为「—」的字段都能明确判断其语义，交叉引用 ID 存在且确实覆盖相应行为。无法确认的字段必须保留为「未验证 / 待确认」。

## R0-RV-04：首页月份切换缺失尚无明确需求依据

**发现位置**

- R0 主报告 §3.1 中 `I-HOME-02` 及相关首页交互记录。
- 该项当前表述为「首页月份切换控件缺失」，并说明是本轮观察项、无既有 R0-E 编号。

**证据与问题**

首页存在「本月收入 / 本月支出」摘要，并不能单独推出首页必须提供月份切换控件。月份切换可能属于报表页面，也可能是原型/设计规范明确要求的首页交互；当前记录没有给出足以判定的 PRD、原型或设计规范条款。

因此，在需求证据未补齐前，不能直接把它列为已确认缺陷或计入 R0 缺陷数量。

**修改要求**

1. 对照 PRD、原型流程和《FastLedger-Web设计规范》逐项查证首页月份切换是否为明确要求。
2. 若有明确要求，引用具体文件、章节/原型页面和可复核证据，再按规范编号登记。
3. 若无明确要求，将其改为「待 Owner 裁决的交互建议」，移出已确认缺陷统计；不得擅自扩大需求范围。

**验收标准**

该项最终只有两种可接受状态：
- 有明确需求证据：形成可追溯的缺陷编号、证据和验收条件；
- 无明确需求证据：标为 Owner 待裁决，不计入已确认缺陷、不阻断 R0 的需求符合性统计，但 Owner 决策仍需记录。
