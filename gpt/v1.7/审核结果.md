## 二、GPT-R26（13 字段）

### 1. id
GPT-R26

### 2. title
转账对侧缺失或关联错误时，删除/恢复仍继续执行单边或错误分组操作

### 3. severity
P1 — 会计正确性与数据完整性。WBS 4.2 明确要求整笔操作并禁止单边路径；当前实现对异常配对没有失败关闭。

### 4. location
- server/internal/service/tx.go:953–970：collectTransferGroup
- server/internal/service/tx.go:798–820：mutateVisibility 加载分组后逐行反向余额、软删与审计
- docs/FastLedger-开发WBS.md:98：4.2「以整笔为单位……禁止单边路径」

### 5. quote
~~~go
if !has {
    // 对侧已不在预期状态：仍按"整笔"处理存在的这一侧，避免悬空配对
    return []*model.Transaction{row}, nil
}
return []*model.Transaction{row, &counterpart}, nil
~~~

对侧查询条件只有 id、book_id、deleted；没有校验对侧也是转账、related_id 反向指回当前行、方向相反、金额与账户配对关系一致。

### 6. problem
转账行只要 TxType=Transfer 且 RelatedId>0，就进入对侧查询。对侧不存在或 deleted 状态不符时，函数返回单行且不报错；调用方随后仍会对该行执行余额反向、状态更新和审计，形成单边删除/恢复。

更严重的是：若 related_id 错指向同账本内另一条普通交易，当前查询会把该普通交易当成转账对侧，随后对两行都反向余额并软删/恢复。该函数没有验证双向配对关系。

### 7. reproduce
1. 在真实 SQLite 测试库创建一笔转账（转出、转入两行）及一笔独立普通交易。
2. 通过测试 SQL 将转账一侧的 related_id 改为独立普通交易的 id，保留相同 book_id 且两行均为存活状态。
3. 调用 Delete(转账行 id)。
4. collectTransferGroup 会返回转账行 + 普通交易行；mutateVisibility 会对两行反向余额、软删并写 delete 审计。
5. 另测对侧缺失/删除状态不一致：当前实现返回单行且继续提交，不会拒绝该操作。

### 8. actual
配对不完整或错链时，删除/恢复不会拒绝；可能单边修改，也可能把无关交易纳入分组一起修改。

### 9. expected
只有验证通过的完整双边转账才允许整笔删除/恢复。任何对侧缺失、状态不一致、非转账、非互指、方向/金额/账户不匹配的情况，都应返回明确冲突错误并回滚，不得触碰余额、交易状态、版本和审计。

### 10. impact
可导致转账仅一侧被删除/恢复、余额与交易记录不一致，或误删/误恢复无关交易。直接破坏记账核心正确性。

### 11. suggestion
- 增加 ErrInvalidTransferPair 一类失败关闭错误。
- 对侧必须满足：同 book_id、同 tx_type=transfer、related_id 指回当前 id、deleted 状态相同、direction 一出一入、amount 相同、account_id/to_account_id 对应。
- 分组结果必须严格为 2 行；不满足即整笔回滚。
- 增加对侧不存在、已删除、错指普通交易、非互指、金额/账户/方向不匹配的真实 SQLite 回归用例。

### 12. status
待确认（提交 owner 裁决；尚未修改业务代码）。

### 13. evidence
当前 main 的 tx.go:953–970 明确在 !has 时返回单行且 nil error；tx.go:798 后调用方对 group 逐行做余额反向、UPDATE、审计。WBS 4.2 明确要求整笔与禁止单边路径。现有 tx_delete_integration_test.go 覆盖正常转账双边删除，但未覆盖损坏配对时失败关闭。本轮未执行测试。

## 三、GPT-R27（13 字段）

### 1. id
GPT-R27

### 2. title
回收站/审计保留天数乘法溢出可将清理截止时间推至未来并清空历史数据

### 3. severity
P1 — 数据丢失。db purge 是破坏性运维命令，溢出后会把原本只应删除到期记录的条件扩大到几乎所有记录。

### 4. location
- server/cmd/server/main.go:239–290：CLI 接受任意正整数，parsePositiveInt 仅检查 Atoi 与 >0
- server/internal/service/recycle.go:58–68：回收站 cutoff 计算及 DELETE
- server/internal/service/recycle.go:79–90：审计 cutoff 计算及 DELETE

### 5. quote
~~~go
func parsePositiveInt(s string, def int) int {
    if n, err := strconv.Atoi(s); err == nil && n > 0 {
        return n
    }
    return def
}
~~~

~~~go
cutoff := now - int64(ttlDays)*secondsPerDay
DELETE FROM transactions
 WHERE book_id = ? AND deleted = 1 AND deleted_at > 0 AND deleted_at <= ?
~~~

审计清理也使用同样的乘法：now - int64(retentionDays)*secondsPerDay。

### 6. problem
只验证正数不足以保证 int64(retentionDays)*86400 不溢出。64 位环境下，足够大的正整数可通过 strconv.Atoi；乘法溢出后结果变成负数，now 减去负数得到远未来 cutoff。于是所有 deleted_at>0 的墓碑都满足 deleted_at<=cutoff，审计表中几乎所有 at 也满足 at<=cutoff。

### 7. reproduce
在 64 位 Go 环境执行：
~~~bash
fastledger db purge --recycle-ttl-days 110000000000000 --audit-retention-days 110000000000000
~~~
该值可被 64 位 int 解析，但乘以 86400 超出 int64。溢出后 cutoff 变为远未来时间，回收站 DELETE 会清除所有正 deleted_at 的墓碑，审计 DELETE 会清除所有正常时间戳的审计记录。此处是按 Go int64 算术规则推导的静态复现，本轮未执行命令。

### 8. actual
保留天数没有合理上限或乘法溢出检查；溢出后的 cutoff 仍被直接用于 DELETE。

### 9. expected
任何超出安全范围的保留天数必须在执行任何 DELETE 之前拒绝；cutoff 计算应有显式溢出保护。异常配置不能回落为未来时间，也不能开始清理。

### 10. impact
一次误配置或恶意传入的超大值即可批量清除回收站墓碑和审计历史，无法通过普通恢复流程还原，属于直接数据丢失。

### 11. suggestion
- 在配置解析层设置有业务意义的最大天数，并在服务函数内再次验证。
- 使用 checked multiplication / checked subtraction，验证 secondsPerDay * days 不溢出且 cutoff 合法。
- 解析到非法或越界值时应报错退出，不要静默回落默认值。
- 为 recycle 与 audit 各增加 MaxInt64 边界、溢出值、0、负数测试；测试必须断言数据库行数完全不变。

### 12. status
待确认（提交 owner 裁决；尚未修改业务代码）。

### 13. evidence
main.go:286–290 只做正整数解析；recycle.go:65、86 均直接进行 int64 乘法后用于 DELETE。当前 CI 170 PASS 记录不能证明未覆盖的溢出边界安全。本轮未执行测试。

## 四、GPT-R28（13 字段）

### 1. id
GPT-R28

### 2. title
删除/恢复与成员管理在事务外读取角色，存在权限撤销后的 TOCTOU 窗口

### 3. severity
P1 — 授权边界缺陷。权限撤销或降权与敏感操作并发时，旧角色可能继续被用于授权。

### 4. location
- server/internal/service/tx.go:756–774：RoleOf 在事务 Begin 之前执行
- server/internal/service/member.go:118–150、172–198：ChangeRole/Remove 在事务 Begin 之前读取 actorRole
- server/internal/service/book.go:216–246：SetVisibility 在事务 Begin 之前读取角色
- server/internal/service/book.go:211–263：完整配置修改路径

### 5. quote
~~~go
role, err := RoleOf(s.engine, bookID, uid)
// ...
canEditOthers := CanEditOthersTx(role)

sess := s.engine.NewSession()
...
if err := sess.Begin(); err != nil {
    return 0, err
}
~~~

MemberService.ChangeRole/Remove 与 BookService.SetVisibility 也采用先 RoleOf(engine,...)、后 NewSession/Begin 的顺序。

### 6. problem
授权依据是在事务外读取的。读取角色与开始写事务之间，另一个请求可以移除该成员或降低其角色。后续敏感操作仍使用旧 role/canEditOthers 继续执行。

例如普通 member 发起删除自己的交易，在 RoleOf 返回成功后被 owner 移除；删除请求随后开始事务，但事务内没有重新验证成员资格，仍可完成删除。若旧角色为 admin，降权后仍可能继续执行管理操作。

### 7. reproduce
1. 建立 owner、admin、member 与一笔 member 创建的交易。
2. 在 Delete 的 RoleOf 返回后、sess.Begin 前设置测试 barrier。
3. owner 并发 Remove(member) 或将 admin 降为 member。
4. 放行 Delete/ChangeRole/Remove/SetVisibility。
5. 当前实现会使用先前读取的角色继续写入；预期应因事务内重新授权失败并且不产生业务写入、版本变化或审计。

### 8. actual
授权检查与业务事务分离；事务内未重新验证 actor 的当前成员资格/角色。敏感写入可能在权限已撤销后继续执行。

### 9. expected
每次敏感操作的权限检查必须与业务写入处于同一事务边界，使用同一 session 读取当前 actor 成员关系及角色；权限不再满足时整体回滚。

### 10. impact
被移除成员可能在移除后仍成功删除/恢复交易；被降权管理员可能在降权后继续执行成员管理或配置操作。涉及账本权限边界与数据完整性。

### 11. suggestion
- 将角色/成员资格读取移入写事务，并在事务内重新校验。
- Delete/Restore 同时在事务内读取 actor role 与交易行；成员管理、可见性修改也采用同一模式。
- 对 SQLite 当前连接池/事务锁策略做并发验证；用 barrier 测试精确控制“授权读取—撤权—写入”顺序。
- 确认撤权事务与敏感写事务的串行化顺序，确保先提交撤权后敏感操作必然失败。

### 12. status
待确认（提交 owner 裁决；尚未修改业务代码）。

### 13. evidence
tx.go:757 在 sess.Begin（L771）前读取 RoleOf；member.go:119、173 与 book.go:220 同样先在 engine 上查角色，随后才开启 session。事务内部没有重新读取 actor role。本轮静态审查，未执行并发测试。

## 五、GPT-R29（13 字段）

### 1. id
GPT-R29

### 2. title
成员/配置变更的 before_json 在事务外读取，并发更新时可能记录错误的变更前状态

### 3. severity
P2 — 审计可信度与可追溯性缺陷。审计行虽然与最终写入处于同一事务，但快照来源可能已经过期。

### 4. location
- server/internal/service/book.go:216–246、254–257
- server/internal/service/member.go:130–162、180–209

### 5. quote
~~~go
b, err := s.Get(bookID)
// ...
oldCanView := b.MembersCanViewOthers
// ...
sess := s.engine.NewSession()
if err := sess.Begin(); err != nil { ... }
~~~

~~~go
targetRole, err := RoleOf(s.engine, bookID, targetUid)
// ...
sess := s.engine.NewSession()
if err := sess.Begin(); err != nil { ... }
// ...
map[string]interface{}{"uid": targetUid, "role": targetRole}
~~~

### 6. problem
before_json 的旧值在事务开始前读取。两个并发配置请求都可能读取旧值 true；第一个提交 true→false 后，第二个仍拿着旧快照执行写入并记录 before=true，即使第二个请求开始时数据库当前值已经是 false。ChangeRole/Remove 的 targetRole 也有同类问题。

### 7. reproduce
1. 将账本可见性初值设为 true。
2. 并发发起两个 SetVisibility(false)，在两者读取 b 后设置 barrier。
3. 先让请求 A 提交，再放行请求 B。
4. 检查两条 config_change 审计：第二条不应声称旧值仍为 true；若当前值已是 false，第二次设置应按幂等操作不写审计。
5. 对 ChangeRole 以两个不同目标角色请求执行同样的并发测试，核对 before_json。

### 8. actual
审计 before_json 可能记录事务开始前的过期值，甚至为一个实际上没有发生状态变化的幂等设置写入“变更”审计。

### 9. expected
旧状态必须从写事务内读取；只有当前值与目标值确实不同才更新并写审计。before_json 必须准确对应本次事务真正覆盖的旧值。

### 10. impact
审计记录不能可靠还原成员权限与配置变更的真实先后状态，降低安全事件调查与责任追溯的可信度。

### 11. suggestion
在事务 Begin 后，用同一 sess 读取账本/成员当前状态，完成权限校验、比较、更新和 insertAudit；将 before_json 从事务内读取的旧实体构造。增加并发重复设置、并发角色修改测试。

### 12. status
待确认（提交 owner 裁决；尚未修改业务代码）。

### 13. evidence
book.go:216、220、232 在事务 Begin（238）之前读取账本与角色；member.go:130、180 在事务 Begin（141、188）之前读取目标角色，随后将该快照写入审计。本轮未执行并发测试。
