## 一、结论

本轮登记 **1 项待 owner 裁决的新问题：GPT-R24（P1）**。

问题是：移除成员后，API 先刷新 Hub 订阅，导致目标用户从账本订阅表中被摘除；随后发出的 `member_removed` 又走普通“仅发给当前订阅者”的广播路径，因此**在线的被移除用户收不到本应触发本地账本数据清理的事件**。

该结论由当前调用顺序、订阅删除分支和广播过滤分支共同支持。它与 [1.27] 已修复的“被移除者仍继续收到后续账本事件”是相反方向、但必须同时满足的两条约束：
- 被移除者不能再收到后续账本事件；
- 被移除者必须收到一次清理通知。

本轮没有执行运行时复现，故状态保持“待确认”，没有写成“已采纳”或“已修复”。

### 5. quote

```go

    ws.DefaultHub.RefreshVisibility(bookID)
    broadcastBookEvent(bookID, bookEventEnvelope{
        Event:           eventMemberRemoved,
        Version:         version,
```

`hub.go` 的非成员处理：

`BroadcastToBook` 的投递条件：

### 6. problem
`MemberService.Remove` 成功后，`notifyMemberRemoved` 先调用 `RefreshVisibility`。该函数对已不再是账本成员的 UID 得到 `member=false`，并删除其连接的 `BookIds[bookID]`。之后 `broadcastBookEvent` 调用 `BroadcastToBook`；后者只向 `BookIds[bookID]` 仍为 true 的连接投递。目标用户因此被过滤掉，收不到 `member_removed`。

### 7. reproduce
静态复核路径（本轮未运行集成测试）：
1. 用户 A、B 同时在线，B 已订阅账本 X。
2. A 成功调用移除 B 的成员接口。
3. 跟踪 `removeMember → notifyMemberRemoved → RefreshVisibility`：成员关系已删除，B 的订阅被从 `BookIds` 删除。
4. 继续跟踪 `broadcastBookEvent → BroadcastToBook`：B 的 `sub` 为 false，命中 `if !sub || send == nil { continue }`。
5. 因而 B 的连接不会收到该 `member_removed` 消息。

### 8. actual
对移除时仍在线且已订阅的目标连接，当前代码先删除订阅，再进行普通账本广播；目标连接因此不会收到 `member_removed`。客户端不能依赖该事件执行 PRD 规定的主动清理。

### 9. expected
- 目标用户收到且仅收到一次针对自己的 `member_removed` 清理通知；
- 其他仍有权限的成员收到正常账本级协调事件；
- 清理通知入队后，目标用户不得再收到该账本的 `data_changed` 或其他后续事件；
- 目标用户离线时，重连/重新订阅被拒绝的路径也应有客户端清理该账本本地数据的明确协议（当前客户端链路不在本轮验证范围）。

### 10. impact
PRD §7.3 / §12.1 要求被移除成员清除该账本本地数据并停止订阅。在线目标客户端收不到清理事件，可能继续保留已同步的账本数据。该问题触及家庭财务隐私，按统一刻度列为 P1。当前证据证明的是通知不可达，不证明所有客户端一定会永久保留数据。

### 11. suggestion
1. 将“给目标用户投递一次清理事件”与“撤销其后续订阅”拆开处理。建议 Hub 提供按 `targetUid` 定向入队的清理通知能力，不经过普通订阅过滤。
2. 确保清理事件成功入队后，再删除目标连接的订阅；该操作需遵循既有 `Hub.mu → Client.mu` 锁序，避免引入锁反转或竞态。
3. 普通账本广播仍发给其他有效订阅者；不要为了通知目标而重新开放其订阅。
4. 增加 Hub/API 集成回归：目标收到清理事件；其他成员正常收到；目标后续收不到 `data_changed`；多连接、断线、重复移除和并发广播均安全。
5. 对离线目标明确重连语义：若重新订阅因非成员被拒绝，客户端必须删除该账本本地缓存；该点需与客户端实现一并验收。

## 五、复核与处置（WorkBuddy，[1.30]）

> 按《多AI对齐规范》§5 状态机回填：`待确认` → **`已修复`**。

### 1. 取证结论：**GPT-R24 属实**

逐行核对（与报告给出的位置一致）：

- `broadcast.go` 的 `notifyMemberRemoved` 原实现是 `RefreshVisibility(bookID)` → `broadcastBookEvent(...)`，没有按 `targetUid` 直投的旁路；
- `hub.go` 的 `RefreshVisibility` 在 `!d.member` 分支执行 `delete(t.c.BookIds, bookID)`；
- `BroadcastToBook` 的投递条件为 `if !sub || send == nil { continue }`。

→ 目标连接在广播前已被摘除订阅，**必然被过滤**，收不到 `member_removed`。属确定性控制流缺口，不依赖时序竞态。

### 2. 这条与 [1.27] 的关系（值得记一笔）

`[1.27]` 修 P3"被移除成员仍留在订阅表"时，**把 ① 做对了却破坏了 ②**：

| 约束 | 方向 | 状态 |
|---|---|---|
| ① 被移除者不能再收到该账本的后续事件 | 收紧 | `[1.27]` 已实现 |
| ② 被移除者必须收到一次清理通知 | 放松（仅一次） | `[1.27]` 破坏，本项修复 |

**教训**：这两条是"同一动作的两个相反要求"，只做其中一条都是错的；而当时的测试只覆盖了 ①（"踢出后收不到广播"），反而会**奖励**错误实现。修复时补的两条 api 用例正是针对 ②。

### 3. 落地修复（[1.30]）

| 位置 | 改动 |
|---|---|
| `internal/ws/hub.go` | 新增 `DeliverToUser(uid int64, msg []byte) int`：向该 uid 的**全部在线连接**定向投递，**不经订阅过滤**；锁序仍 `Hub.mu(读) → Client.mu`；非阻塞，`Send` 满则 `Dropped++`；返回入队连接数（`0` = 离线或缓冲满） |
| `internal/api/broadcast.go` | `notifyMemberRemoved` 改为三段固定顺序：**① `RefreshVisibility`（撤销订阅）→ ② `DeliverToUser`（定向投递一次）→ ③ `BroadcastToBook`（其余有效订阅者）**；抽出 `marshalBookEvent` 让两条路径复用同一份字节 |
| 日志 | 目标离线/缓冲满时记 `member_removed 未送达目标`，便于排查"某设备残留已退出账本数据" |
| 客户端契约 | 重连后订阅被拒（已非成员）→ 必须删除该账本本地缓存（写入 `落地方案 §5.2` 的对应说明） |
