## 一、结论摘要

<badge>1 项新 finding</badge>

发现 **1 项 P1 隐私/数据清理问题：成员被移除后，服务端先从 Hub 订阅表摘除该成员，再广播 `member_removed`；因此被移除成员的在线客户端收不到本应触发本地账本数据清理的事件**。

该问题不是旧 D-R05/D-R07 等已修问题的重复：此前修复的是“被移除者仍继续收到后续账本事件”；当前实现解决了停止后续订阅，却把“通知被移除端清除本地数据”一并截断。两项要求应同时满足。

## 二、GPT-R24 · 被移除成员在取消订阅前未收到清理通知

- `id`：GPT-R24
- `title`：先摘除 WS 订阅再广播 member_removed，导致被移除端收不到本地数据清理通知
- `severity`：**P1**
- `location`：
  - `server/internal/api/broadcast.go` §notifyMemberRemoved，L135–142
  - `server/internal/ws/hub.go` §RefreshVisibility，L294–380（关键摘除逻辑 L369–375）
  - `server/internal/ws/hub.go` §BroadcastToBook，L236–262（仅向仍订阅该账本的连接投递，L254–258）
  - 需求依据：`docs/FastLedger-产品需求文档-PRD.md` §12.1 决策 5，L561；§10.4，L420
- `quote`：

```go
func notifyMemberRemoved(bookID, version, targetUid int64) {
    ws.DefaultHub.RefreshVisibility(bookID)
    broadcastBookEvent(bookID, bookEventEnvelope{
        Event: eventMemberRemoved,
        Version: version,
        ForceFullResync: true,
        Data: map[string]interface{}{"targetUid": targetUid},
    })
}
```

以及 `RefreshVisibility` 对非成员的处理：

```go
if !d.member {
    delete(t.c.BookIds, bookID)
    delete(t.c.canView, bookID)
    t.c.visSeq[bookID]++
    t.c.mu.Unlock()
    continue
}
```

- `problem`：`notifyMemberRemoved` 先调用 `RefreshVisibility`，再调用 `broadcastBookEvent`。成员移除后，`CanViewDetail` 对目标用户返回非成员错误；`RefreshVisibility` 因而删除其 `BookIds[bookID]`。随后 `BroadcastToBook` 只向 `BookIds[bookID]` 仍为 true 的连接发送消息，目标用户的连接已不满足订阅条件。故 `member_removed` 不会送达目标客户端。
- `reproduce`：
  1. 用户 A、B 均在线并已订阅同一账本；B 的本地客户端已有该账本缓存。
  2. A 调用移除 B 的成员接口；确认 `MemberService.Remove` 成功。
  3. 跟踪 `book_handler.go` 的 `removeMember` → `notifyMemberRemoved` → `RefreshVisibility` → `BroadcastToBook`。
  4. 在 Refresh 阶段确认 B 的 `BookIds[bookID]` 被删除；在 Broadcast 阶段确认 B 被 `if !sub` 跳过。
  5. 观察 B 客户端：收不到 `member_removed`，无法按协议自动清除该账本本地数据。
  - 本轮未运行上述集成步骤；这是依据当前源码分支与状态变更顺序得出的静态可证结论。
- `actual`：目标用户的 WS 订阅被移除，随后广播不会把 `member_removed` 投递给目标用户。其客户端可能继续保留此前已同步到本地的账本数据，且不会收到协议规定的主动清理信号。
- `expected`：被移除用户必须在失去后续订阅资格的同时，先收到一次仅针对自己的 `member_removed` 清理通知；其他仍有权限的成员继续正常收到该事件。清理通知不能重新开放该用户的账本订阅，也不能让其收到后续 `data_changed`。
- `impact`：PRD 明确要求被移除成员收到事件后清除该账本全部本地数据并停止订阅。当前顺序导致客户端本地缓存未被告知清理，已移除成员设备可能继续显示家庭账目、余额与历史交易。该问题涉及家庭财务隐私，定为 P1。
- `suggestion`：
  1. 将“通知被移除目标”与“撤销其后续订阅”拆成两个明确动作：先向目标 UID 的在线连接定向发送 `member_removed`（不通过普通账本订阅过滤），再完成 RefreshVisibility 摘除；或在 Hub 提供原子化的 `RemoveSubscriptionAndNotify`，在同一 Hub/Client 锁序下先入队清理事件再删除订阅。
  2. 仍向其他成员广播账本级 `member_removed`，并确保目标连接在清理通知入队后不能再收到任何账本后续事件。
  3. 增加回归测试：目标连接收到且只收到清理事件；非目标成员收到普通广播；目标连接在后续 `data_changed` 中不再收到消息；重复移除/断线竞争不 panic、不死锁。
- `status`：**待确认**（等待 owner 裁决）
- `evidence`：当前 main 源码静态核实：`broadcast.go:135–142` 的调用顺序为 RefreshVisibility 在前、广播在后；`hub.go:369–375` 对非成员删除 BookIds；`hub.go:254–258` 广播仅对已订阅连接发送。PRD §12.1 决策 5（L561）要求被移除成员收到 `member_removed` 后清除该账本本地数据。未执行运行时复现，建议补真实 Hub/WS 集成测试。
